## Что это

Telegram-агент, который по свободному тексту (RU/EN) **читает и изменяет** кампании Google Ads на уровне
MCC. Топик супергруппы = клиент. Агент — **исполнитель, не автономный оптимизатор**: перед любым изменением
показывает «было → станет» и ждёт подтверждения.

```
Менеджер в топике клиента: «разберись почему упали заявки»
  ↓ агент подтягивает скилы + память + профиль клиента
  ↓ агентский цикл: get_stats → get_search_terms → get_auction_insights → …
  ↓ уточняет текстом, продолжает после ответа
  ↓ propose_change → черновик в БД с diff «было → станет»   ← Google Ads НЕ тронут
  ↓ сводка текстом, БЕЗ кнопок
  ↓ менеджер РЕПЛАЕМ на это сообщение: «да»                 ← распознаёт КОД по закрытому списку
  ↓ 9 проверок fail-closed (§2.2) → ads/mutations.py → audit-row
  ↓ отчёт «выполнено» ИЗ AUDIT-ROW, не из текста агента
```

## Границы автономии — разрез по типизированному вызову

**Всё до вызова — модель. Сам вызов и всё после — код.** Это не компромисс между «автономный» и
«безопасный»: первое про то, кто думает, второе — про то, кто нажимает.

- **Модель сама, без спроса** (`SPEC.md` §0.2, 13 пунктов): понимает задачу, **выбирает инструменты и их
  последовательность**, решает что прочитать и сколько итераций сделать, **подключает и пишет себе скилы**,
  уточняет, помнит клиента, кластеризует ключи, формулирует **что** предложить.
- **Код, всегда и детерминированно** (§0.3, 13 пунктов): исполняет вызов к API, одноразовость
  подтверждения, провенанс, потолок аккаунта, счёт символов, округление денег по биллинг-единице, все
  производные метрики, whitelist, шифрование токенов, свежесть, аудит, отчёт «выполнено», файлы/расписания.

Ни один пункт §0.3 нельзя отдать модели — не по осторожности, а потому что модель физически не является
тем механизмом, который это делает.

## 🔒 Золотые правила (НЕ нарушать — это про чужие деньги)

1. **Confirm-гейт.** Мутация выполняется ТОЛЬКО после явного согласия человека. Мутация и подтверждение
   **разделены**: агент лишь СОЗДАЁТ черновик (proposal), выполняет — код. Согласие распознаёт **КОД по
   закрытому списку** (`да`, `делай`, `ок`, `подтверждаю`, `go`, `yes`), **не модель**; всё остальное — не
   согласие. Порядок 9 проверок фиксирован и каждая fail-closed — `SPEC.md` §2.2.
   ⚠️ **Статус реализации:** сегодня согласие приходит из кнопочного слоя `bot/`. Закрытого списка слов
   в коде НЕТ, `tg_message_id` никем не пишется, `reply_to_message_id` нигде не читается — реплай-
   транспорт целиком проектируется (Волна 1 шаг 5). Требование от этого не слабее: это то, что обязано
   быть написано, а не то, что уже работает. ⛔ И не «доделывается» через `bot/main.py:300 _LAST_PENDING`
   (chat_id → последний `confirmation_id`): «да» → подтвердить последний черновик не удовлетворяет ни
   одному пункту §2.2.
2. **`confirmation_id` обязателен.** Каждая функция в `ads/mutations.py` принимает `confirmation_id` и
   проверяет, что он соответствует подтверждённой строке. Без него — `raise`. Одноразовость — свойство
   ХРАНИЛИЩА, не рассуждения: атомарный `ConfirmStore.claim`, второй вызов даёт `rowcount=0`
   ([confirm/store.py:194](confirm/store.py#L194)). Привязка реплая — `reply_to_message_id ==
   proposal.tg_message_id` И `actor_chat_id == proposal.author_chat_id` (**целевой контракт §6.4, ещё не
   написан**: `execute_confirmed` сегодня принимает только `(store, confirmation_id)` и про личность
   актора не знает ничего — значит отказать при отсутствии доверенной записи не может, а хуки Hermes
   фейлятся OPEN). Проверять придётся по `user_id`: `confirm/store.py:271` сверяет `chat_id`, что в
   private случайно совпадает с человеком, а в супергруппе вырождается в тождество, не изменившись ни
   строкой; `author_user_id` уже пишется ([confirm/store.py:142](confirm/store.py#L142)) и нигде не сверяется.
3. **Бюджет/ставка — только по прямой команде человека.** Два независимых бита провенанса; второй
   (`origin_human_turn`) **аргументом не задаётся вовсе** — штампует доверенный слой в момент СОЗДАНИЯ
   черновика ([core/provenance.py:43,54](core/provenance.py#L43)). **Подтверждение человеком бит НЕ
   повышает** — иначе проверка тождественно истинна: cron предлагает поднять бюджет → человек говорит «да»
   → бит `True` → защита не срабатывает никогда. Никогда из scheduler/anomaly.
4. **Длину символов считает КОД, а не модель.** RSA: headline ≤30, description ≤90, path ≤15. **Кириллица =
   1 символ** (двойная ширина только у CJK). Считать по Unicode code points (`len(str)`), НЕ по UTF-8
   байтам. Перегенерировать, если превышено. Реализация — `adcopy/validate.py`.
5. **Секреты — никогда в промпт, логи, гит И ЛЮБОЙ выход наружу.** Токены/ключи только из env/секрет-
   хранилища, в конфиге — `SecretStr`; refresh-токены в БД шифруются at-rest (`core/secrets.py`). Наружу
   текст идёт только редактированным: логи — `core.logging.redact_text`, Telegram — `bot.ux.err_text`.
   **Сырой `str(e)` пользователю не слать** (исключение от google-ads/OpenAI может нести токен). Три рубежа
   редакции — [`docs/SECURITY.md`](docs/SECURITY.md).
6. **Ни Hermes, ни модель не трогают SDK напрямую.** Модель заполняет типизированную (Pydantic) схему → наш
   код валидирует диапазоны → показывает diff → ждёт согласия → вызывает `google-ads` SDK → пишет
   audit-row. **Правило тонкого слоя (§5.5):** слой инструментов = валидация входа + вызов существующей
   функции + сериализация ответа. Захотелось написать в нём логику — её место в `ads/` или `confirm/`.
7. **Разработка — только на Draft/test-аккаунте.** Боевые аккаунты трогает только развёрнутый контур с
   полным гейтом. Прототипы, отладка, дев-скрипты — на тест.
8. **Жёсткий allow-list операций.** Агент может вызывать только инструменты из реестра `SPEC.md` §6.
   **Approvals Hermes наши инструменты НЕ покрывают** (только терминальные команды) — право «кто может
   дёрнуть мутацию» живёт **целиком в нашем слое**. Возможность закрывается ровно одним способом: набор
   инструментов не регистрируется вовсе; списки запрещённого — defense-in-depth, не граница.
9. **Замок аккаунта — ЧТЕНИЕ и МУТАЦИИ раздельно.**
   - Мутации: единственный чокпойнт `ads.client.ensure_allowed(customer_id)`. Мутировать можно ТОЛЬКО
     аккаунт, **видимый боту** (набор ⊆ `allowed_ceiling()`), — чужой боевой id по опечатке не пройдёт.
     КОД-минимум `ALLOWED_CEILING = {Draft 7753643025}` через env не понижается.
   - Прод-дефолт — сентинел `GOOGLE_ADS_ALLOWED_CUSTOMER_IDS=all` (мутации на всех видимых, решение
     владельца 2026-07); явный список id **сужает** набор; в dev/test пусто ⇒ мутаций нет вовсе
     (**fail-closed**).
   - Чтение: ОТДЕЛЬНЫЙ, более широкий чокпойнт `ensure_read_allowed(customer_id)` + пер-пользовательский
     грант (`core.access`, `/grant`). **Грант чтения НЕ открывает мутации.**
   - Исполнение привязано к черновику: `execute_confirmed` берёт аккаунт из `proposal.customer_id` и ЗАНОВО
     проходит `ensure_allowed` — не из аргумента и не из контекста разговора.
   - **Точный контракт потолка, режимы `ACCOUNT_ACCESS_MODE`, имена инвариант-тестов —
     [`docs/SECURITY.md`](docs/SECURITY.md). Правишь замок — читай его сначала.**
10. **Fail-closed везде (никогда fail-open).** Любой гейт при отсутствии конфигурации ОТКАЗЫВАЕТ, не
    открывает: whitelist (env `TELEGRAM_WHITELIST_CHAT_IDS` ∪ БД-таблица `whitelist`) при ПУСТОМ
    объединении блокирует ВСЕХ (`if wl and ...` — это fail-open, так нельзя); сбой БД ⇒ пустой БД-набор, а
    не проход; `ensure_allowed`/`ensure_manager_allowed` при пустом allow-list — отказ; `user_initiated` по
    умолчанию `False`. В `prod` пустой whitelist или отсутствие ключа шифрования роняют старт (fail-fast,
    `core.config`). Дев-скрипты с прямой записью (минуя confirm-гейт) — только `ENV=dev`.
11. **И4 — инструменты мутации ФИЗИЧЕСКИ недоступны в read-фазе.** Не «не вызываются», а не существуют:
    construction-time assert в реестре, импорт падает при нарушении.
12. **И7 — таинт внешнего контента.** В ходе, где прочитан external-контент (страница, досье, CSV
    конкурентов), Ads-мутации **физически недоступны**. Prompt injection не решается инструкцией в промпте
    (OWASP LLM01 = #1); рабочая защита — least privilege на уровне инструментов. Таинт ставится по треду
    при первом external-чтении и снимается **только сигналом нового человеческого сообщения** — сам не
    истекает. Два узаконенных исключения (memory-черновик разрешён, Ads-мутации нет): краул сайта клиента →
    профиль (§3.8) и разбор посадочной при генерации RSA (§3.4.1).
13. **И8 — не более одного черновика на ассистентский ход.** Энфорсмент — **счётчик в нашем слое**, не
    надежда на модель: агентский цикл делает много последовательных итераций и создаст N черновиков подряд.
    Отсутствие `parallel_tool_calls` — фон, а не защита (запрещает параллельные вызовы в одном ответе, не
    последовательные итерации). `provider.require_parameters: true` обязателен — OpenRouter молча
    отбрасывает неподдерживаемые параметры.
14. **К1 — `skills.inline_shell: false` НАВСЕГДА.** Иначе `` !`cmd` `` из SKILL.md исполняется на хосте
    **без approval** — RCE мимо гейта подтверждения. Терминал/веб/память/`session_search` у агента
    выключены (`deploy/hermes/config.yaml`), веб-дашборд наружу не выставляется (К3): его REST умеет
    install/uninstall скилов.
15. **К7 — «выполнено» пользователю репортит НАШ КОД из audit-row**, не текст агента. Агент не сверяет
    финальный ответ со статусом вызовов (upstream issue #54722). Истина = audit-row + повторное чтение из
    API.

## Топология — три процесса, не один

| Процесс | Что делает | Что знает |
|---|---|---|
| **Hermes gateway** | Агентский цикл, диалог, скилы, память рантайма | **Только `OPENROUTER_API_KEY`.** Google Ads OAuth не знает вовсе |
| **Слой инструментов** (`mcp_server/`) | Google Ads, отчёты, генерация, память проекта | OAuth-токены, ключ шифрования, БД |
| **Планировщик** | Джобы, алерты, плановые отчёты, уборка | БД + тонкий Bot-клиент для отправки |

Разделение — не украшение: **у Hermes нет ролей**, одобренный пользователь получает права владельца,
включая терминал на сервере. Держать OAuth-токены в том же процессе несовместимо с правилом 5.

## Ядро — Hermes

**Пин `v0.19.0` (тег `v2026.7.20`), автообновление на проде выключено.** Платформа 0.x, релиз каждые 5–10
дней, миграции конфига между версиями; пин — ещё и защита от известных дыр (CVE-2026-53869).

**К10 — Hermes МОЛЧА игнорирует неизвестные ключи конфига.** Опечатка = «конфиг рабочий на вид, но не
работает». Каждый ключ сверяется с эталоном пиновой версии; конфиг-линт (`deploy/hermes/lint_config.py`) —
часть деплой-процедуры. Три реальных случая уже поймано (`memory.providers` вместо `provider`,
несуществующий слаг вспомогательной модели, имя тулсета в списке запрещённых **команд**).

**Что берём готовым, а не строим** (§5.6): Kanban (durable очередь задач + воркеры), Goals (цель,
переживающая ходы, судья-модель), Cron (агент сам ставит себе расписание и доставляет результат в
Telegram), delegation/субагенты, curator. **Что Hermes НЕ даёт и остаётся нашим:** гейт подтверждения
(Kanban завершает задачи по решению воркера, «no mandatory approval gate»), проверка «действительно ли
сделано», изоляция клиентов (И6), весь слой Google Ads.

## Транспорт инструментов — MCP (тул-слой) + плагин-хук (только гейт)

- **MCP-сервер `mcp_server/`** — как Hermes дотягивается до `ads/`/`confirm/`. Отдельный процесс ⇒ OAuth
  изолирован от Hermes (ровно то, чего требует топология). Сейчас 12 READ-инструментов; PLAN/WRITE —
  Волна 1 шаг 5. «MCP не нужно» заказчика относится к **сторонним** MCP; свой сервер над своим кодом — это
  наши инструменты, не сторонняя зависимость.
- **Плагин-хук — ТОЛЬКО доверенный канал метаданных гейта.** `actor_chat_id`/`reply_to_message_id` в
  MCP-вызов приходят из аргументов, которые генерит LLM (нарушение И-Т1) — значит наивная сигнатура даёт
  модели **сфабриковать подтверждение**. Доверенная личность нужна мимо LLM, через хук рантайма.
  ⚠️ **Хуки фейлятся OPEN** («errors in any hook are caught and logged, never crashing the agent»): хук
  поставляет МЕТАДАННЫЕ, решение выносит наш слой. Даже если хук не отработал, `execute_confirmed` обязан
  отказать при отсутствии доверенной записи. Payload меряет проб `deploy/hermes/plugins/aimash_probe`.
- **До подтверждения хотя бы одного канала WRITE-слой в прод не выходит** (§15.2).

## Переходное состояние — что живо СЕГОДНЯ

- Старый бот жив и развёрнут: контейнер `aimash-bot` = `python -m bot.main`.
- Hermes ходит в Google Ads **через него**: `docker exec -i aimash-bot python -m mcp_server`
  ([deploy/hermes/config.yaml:68-76](deploy/hermes/config.yaml#L68-L76)). Только READ.
- **WRITE/PLAN через Hermes НЕ подключены.** Мутации сегодня идут прежним путём.
- ⛔ **`bot/` и `agent/` физически не двигать.** Архивация — после Волны 1 шаг 1 (bot-free энтрипоинт +
  перенос advisory-lock, §5.3 C1/C3), тогда же тег `pre-hermes`. Сегодня перенос убил бы развёрнутый
  READ-путь, а `bot.i18n` утащил бы за собой ещё и `advisor/service.py`, `reports/service.py` (C4).

## Модель (СМЕНЯЕМАЯ — не зашивать одну)

Все вызовы — через **OpenRouter**. Раскладка по ролям — `SPEC.md` §10.1: диалог/research —
`gpt-5.6-terra`, полный аудит — `gpt-5.6-sol` (только на этот сценарий, по явному правилу), копирайт RSA —
`claude-sonnet-5` (метрика выбора = **число ретраев до прохождения валидатора**, а не «красивее»), фон и
карантинный экстрактор — `gemini-3.1-flash-lite`, парсинг/маршрутизация — `gpt-5.6-luna`. Выбор — **по
данным** (`scripts/ab_test_models.py`), не по бренду.

**Запись в кэш платная (1.25× от входа):** системный префикс собирать **детерминированно** (стабильный
порядок инструментов, без timestamp, фиксированный порядок ключей JSON) — иначе платим 1.25× за
перезапись вместо 0.1× за чтение. Это правка кода сборки промпта, а не выбор модели.

## Структура

**Ядро, переносится без изменений — не переписывать:**
- `ads/` — auth, **client (замок аккаунта)**, read (GAQL через paged `Search`), mutations (требуют
  `confirmation_id`), resolve, keyword_plan, assets, freshness, service (`execute_confirmed` — bot-free,
  [ads/service.py:1266](ads/service.py#L1266)).
- `confirm/` — proposal (diff), gate, store (атомарный claim), render, audit.

## Работа в Claude Code

**Экономия контекста** (главная статья расхода — перечитывание всей истории на каждом ходу, не ответы):
- `/clear` между несвязанными задачами. Не тащить мусор прошлой задачи в следующую — это и дешевле, и точнее.
- Разведка по коду («где реализовано X», «что трогает Y») — субагентом `Explore`. Его контекст изолирован:
  в главный поток вернётся вывод, а не дампы двадцати файлов, которые потом перечитываются каждый ход.
- `Grep` / `Read` с offset+limit вместо чтения файла целиком; целиком — только если правишь целиком.
  `SPEC.md` — 200 КБ: читать разделами по оглавлению, а не подряд.
- Тесты точечно: `pytest tests/test_x.py -q`. Полный прогон — перед коммитом.
- Замер расхода: `python scripts/claude_usage.py` (read-only разбор транскриптов; медиана контекста, доли статей).

**Прочее:**
- Архитектура/сложное — Opus 4.8; объём (CRUD, отчёты, тесты, бойлерплейт) — Sonnet 4.6.
- Скилы: `new-mutation`, `gaql-query`, `check-rsa-copy`, `gads-version`, `confirm-gate-audit`.
- Slash-команды (`.claude/commands/`): `/verify-live` (единый вход в live-смоук), `/restart-bot`
  (409/lock/double-import). `/add-bot-command` относится к **архивируемому** слою — новых кнопочных команд
  не заводить, текстовые инструменты идут в реестр `SPEC.md` §6.
- **Windows-консоль:** запускай скрипты с `PYTHONIOENCODING=utf-8` (или зови `scripts/_win_console.enable_utf8()`
  в начале скрипта) — иначе cp1251 роняет emoji/кириллицу `UnicodeEncodeError`.
- **pre-commit гоча:** `ruff-format` переписывает файлы прямо в хуке → 1-й `git commit` падает («files were
  modified by this hook») → повтори `git add -A && git commit` (со ВТОРОГО раза проходит). Пин `ruff==0.14.10`
  синхронен в 3 местах (pyproject `[dev]` / `.pre-commit-config.yaml` / CI) — не бампай одно без остальных.
