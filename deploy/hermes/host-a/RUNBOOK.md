## Зачем отдельная машина

Короткий ответ: **потому что на текущем VPS «read-only агент» невозможен технически.**

Юзер systemd-сервиса Hermes обязан входить в группу `docker` (`deploy/hermes/README.md:104-105`), а
группа `docker` root-эквивалентна. Одна команда `docker exec aimash-bot env` печатает полноправный
OAuth и `SECRETS_ENCRYPTION_KEY`, которым расшифровываются refresh-токены всех клиентов. Агент с
терминалом на том же хосте — это агент с полными правами, сколько бы read-only кредов ему ни выдали.

Отсюда: **Хост A** — новая ВМ, где полноправных кредов нет физически. **Хост B** — текущий VPS
(`167.233.48.243`), где живут Postgres, денежный контур и полные креды. Общих секретов между ними нет.

## 1. ВМ и ОС-пользователь

Минимум: 2 vCPU / 4 GB / 40 GB, Ubuntu 24.04. ~$5–10/мес — единственная новая инфраструктурная статья.

```bash
adduser --disabled-password --gecos "" hermes
# НЕ добавлять в группы docker и sudo. Docker на этом хосте не нужен вовсе —
# именно поэтому MCP запускается через venv-обёртку, а не `docker exec`, как на Хосте B.
loginctl enable-linger hermes        # systemd --user переживает выход из сессии

ufw default deny incoming
ufw allow 22/tcp
ufw enable
```

Входящих портов, кроме SSH, не открывать: Hermes ходит наружу сам (Telegram long polling, OpenRouter,
Google Ads API). **Postgres Хоста B слушает `127.0.0.1:5433`** (`docker-compose.yml:20-23`, комментарий
там же: «наружу (0.0.0.0) НЕ светим») — и открывать его наружу ради Хоста A нельзя. Это не мелочь
конфигурации, а причина, по которой Этап 1 возит карточки «было → станет» через Telegram, а не через БД.

## 2. Google-пользователь с ролью Read only

Делает **владелец руками**, в интерфейсе Google Ads. Автоматизировать нечего и не нужно.

1. Отдельный Google-аккаунт (не личный, не тот, под которым работает бот).
2. MCC `628-373-8601` → Admin → Access and security → «+» → уровень **Read only**.
3. Убедиться, что этот аккаунт **не имеет доступа больше нигде** — ни в одной другой иерархии,
   ни на одном дочернем аккаунте отдельно.

Пункт 3 — не формальность. Уровень доступа это свойство **пары** (пользователь, иерархия), а
иерархию выбирает **вызывающая сторона** заголовком `login-customer-id`. То есть если тот же
пользователь где-то ещё имеет Standard, агент может дотянуться туда, подставив другой
`login-customer-id`. Это путь эскалации, и закрывается он только тем, что таких мест нет.

⚠️ **НЕ ПРОВЕРЕНО:** наследуется ли Read only с MCC на дочерние аккаунты именно в API и как
резолвится конфликт ролей при разных `login-customer-id`. Проверяется шагом 4 — он для этого и нужен.

## 3. Refresh-токен ТОЛЬКО со scope `adwords`

⚠️ **`scripts/get_refresh_token.py` для этого НЕ использовать.** Проверено чтением:
- `SCOPES` (`scripts/get_refresh_token.py:69-73`) запрашивает `adwords` **плюс** `drive.file`
  **плюс** `spreadsheets.readonly` — агенту, который по замыслу не должен ничего кроме чтения
  рекламы, выдаются права на Google Drive и чужие таблицы;
- `save_to_env` (`:82-89`) **перезаписывает `.env` в корне репозитория** — то есть на машине
  разработчика затрёт рабочий токен.

Токен выпускается отдельным одноразовым скриптом, где scope ровно один:

```python
# ~/get_token_readonly.py — на РАБОЧЕЙ машине, не на Хосте A. После использования удалить.
from google_auth_oauthlib.flow import InstalledAppFlow

flow = InstalledAppFlow.from_client_secrets_file(
    "client_secret.json",
    scopes=["https://www.googleapis.com/auth/adwords"],   # ровно один, других не добавлять
)
creds = flow.run_local_server(port=8765, prompt="consent")
print(creds.refresh_token)   # вывести и сразу перенести в ~/.hermes/.env Хоста A
```

Согласие давать **из-под read-only Google-аккаунта из шага 2**, а не из-под своего. Это самая частая
ошибка в этой процедуре: OAuth-клиент общий, а вот кто нажал «разрешить» — определяет всё.
Единственный scope Google Ads API — `https://www.googleapis.com/auth/adwords`; read-only-варианта
не существует (проверено по `developers.google.com/google-ads/api/docs/oauth/internals`), поэтому
потолок держится **ролью пользователя**, а не областью действия токена.

`sha8` полученного токена (его печатает скрипт из шага 4) **обязан отличаться** от `sha8` токена
Хоста B. Совпадение = выпустили токен не под тем аккаунтом.

## 4. Проверка потолка — ДО установки агента

Порядок принципиален: сначала доказать, что креды бессильны, потом давать им терминал.

```bash
# на Хосте A, в venv из шага 5
set -a; . /opt/aimash-read/.env; set +a
python scripts/verify_readonly_ceiling.py --profile a
```

Коды выхода: `0` — потолок подтверждён; `1` — **ПРОБИТ, агента не ставить**; `2` — НЕПОЛНО (часть
периметра не проверена, это НЕ зелёный); `3` — ошибка конфигурации.

Скрипт не читает роль (из-под read-only она недоступна) — он **пытается** создать бюджет с
`validate_only=True` в каждом видимом аккаунте. Единственное принимаемое доказательство —
`authorization_error.ACTION_NOT_PERMITTED`. `USER_PERMISSION_DENIED` доказательством **не** считается:
это «нет доступа к аккаунту», а не «доступ только на чтение», и именно на этой подмене проверка
давала бы ложный зелёный.

**Негативный контроль обязателен.** Цепочка «отказ везде» одинаково выглядит и при исправном потолке,
и при сломанном зонде. Поэтому тот же скрипт запускается на **Хосте B** с полными кредами:

```bash
# на Хосте B, аккаунт Draft
python scripts/verify_readonly_ceiling.py --profile b --account 7753643025
# обязан НАПЕЧАТАТЬ «НЕГАТИВНЫЙ КОНТРОЛЬ ПРОЙДЕН» и выйти с кодом 0
```
Без пройденного негативного контроля зелёный результат профиля `a` не значит ничего.

⚠️ **Скрипт ни разу не запускался против живого API** — ни на одном хосте, ни с какими кредами.
Проверено локально: он компилируется, проходит `ruff check`, корректно отрабатывает ветки «нет
кредов» и «плохие креды», а сборка зонда и расшифровка кода ошибки сверены интроспекцией SDK
(`validate_only` доезжает до запроса; декодер даёт ровно `authorization_error.ACTION_NOT_PERMITTED`).
Первый живой запуск — **на Хосте B с `--profile b`**, где цена ошибки нулевая: `validate_only=True`
ничего не создаёт.

Периодичность: раз в сутки **кроном с Хоста B** (по SSH), а не с Хоста A. На Хосте A крон завёл бы
агент — то есть проверяемый проверял бы сам себя.

## 5. MCP-READ на Хосте A

⚠️ **Как есть — не заработает.** Три независимые причины, каждая проверена по коду:

1. `bootstrap_ads_layer()` при недоступной БД кидает `RuntimeError` (`app/bootstrap.py:62-66`,
   fail-closed сознательный) и следом требует `assert_schema_at_head()` (`:72`) — то есть нужна не
   просто БД, а **накатанная схема**;
2. пакеты `app` и `audit` до 21.07 отсутствовали в `[tool.setuptools.packages.find] include`
   (`pyproject.toml:67-68`) ⇒ `pip install -e .` их не ставил, и `python -m mcp_server` падал на
   импорте. **Исправлено, класс закрыт тестом** `tests/test_packaging.py`;
3. `core/config.py:29` читает `.env` **относительным путём** — то есть из текущего каталога. Запуск
   из другого места молча стартует с дефолтами.

Установка:

```bash
mkdir -p /opt/aimash-read && cd /opt/aimash-read
git clone <репозиторий> src && cd src
python3.12 -m venv /opt/aimash-read/venv
/opt/aimash-read/venv/bin/pip install -e .

cat > /opt/aimash-read/.env <<'EOF'
ENV=test
DATABASE_URL=sqlite+aiosqlite:////opt/aimash-read/state.db
GOOGLE_ADS_DEVELOPER_TOKEN=...
GOOGLE_ADS_CLIENT_ID=...
GOOGLE_ADS_CLIENT_SECRET=...
GOOGLE_ADS_REFRESH_TOKEN=...
GOOGLE_ADS_LOGIN_CUSTOMER_ID=6283738601
GOOGLE_ADS_READ_CUSTOMER_IDS=
GOOGLE_ADS_ALLOWED_CUSTOMER_IDS=
EOF
chmod 600 /opt/aimash-read/.env

cd /opt/aimash-read/src && /opt/aimash-read/venv/bin/alembic upgrade head
```

Про эти переменные по отдельности:
- **`SECRETS_ENCRYPTION_KEY` не задавать никогда.** С ним `load_oauth_cache` расшифрует чужие
  **полноправные** per-account токены прямо в память процесса — то есть вернёт на Хост A ровно то,
  ради отсутствия чего он и заведён;
- **`GOOGLE_ADS_ALLOWED_CUSTOMER_IDS` пустой** — мутационный allow-list, при пустом значении
  `ensure_allowed` отказывает всем (fail-closed). На Хосте A мутаций нет и быть не должно;
- **`ENV=test`**, не `dev` и не `prod`: `dev` открывает demo-скрипты прямой записи мимо confirm-гейта,
  `prod` требует ключ шифрования и ставит `ALLOWED=all`;
- `GOOGLE_ADS_READ_CUSTOMER_IDS` пуст — читаемый набор наберётся обходом MCC.

Все четыре пункта проверяет сам скрипт из шага 4 (`hygiene_host_a`) и отказывается признавать
результат зелёным, если что-то нарушено.

Обёртка, на которую ссылается `config.yaml`:

```bash
cat > /opt/aimash-read/bin/mcp-read <<'EOF'
#!/bin/sh
# cd обязателен: core/config.py:29 читает .env относительным путём.
cd /opt/aimash-read/src || exit 1
set -a; . /opt/aimash-read/.env; set +a
exec /opt/aimash-read/venv/bin/python -m mcp_server
EOF
chmod 755 /opt/aimash-read/bin/mcp-read
```

Проверка до подключения к агенту: `/opt/aimash-read/bin/mcp-read` должен подняться и не упасть на
`init_db` (по stdio он ждёт JSON-RPC — достаточно, что процесс жив и не выплюнул traceback).


Честно про `chattr`: он мешает случайной перезаписи и заставляет агента, который решит поправить себе

`hermes --yolo` конфига вообще не спрашивает. **Границей остаётся только роль Google-пользователя.**
