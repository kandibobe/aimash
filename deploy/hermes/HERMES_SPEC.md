## Context

**Зачем.** Aimash сегодня — кнопочный Telegram-бот: фраза → модель за один проход выбирает один
инструмент → карточка «было → станет» → нажатие ✅. Он не помнит вчерашний разговор, не собирает
картину из нескольких запросов, не накапливает знание о клиенте и не умеет писать себе инструкции
под повторяющиеся задачи.

**Куда идём.** Ядром становится [Hermes Agent](https://github.com/NousResearch/hermes-agent) —
он даёт то, чего в проекте нет и что дорого писать: агентский цикл, память между сессиями,
библиотеку скилов с самонаписанием и курированием, глубокую интеграцию с Telegram-группами и
forum-топиками. Кнопки уходят полностью: общение текстом, подтверждение — реплаем «да».

**Что Hermes НЕ даёт и что остаётся нашим.** Ни в ~70+ встроенных скилах, ни в ~100+ опциональных
(73/104 на 20.07, числа плавают между релизами) **нет ни одного рекламного скила**; списки
«awesome-hermes-agent» — коммьюнити, не NousResearch. Google Ads API в Hermes отсутствует. В широкой
экосистеме рекламное уже появляется: официальный `google/skills` (скилы установки Google Ads MCP),
хаб marketingskills.sh, и с 28.04.2026 — **официальный Google Ads MCP-сервер
(`googleads/google-ads-mcp`): read-only by design, 3 generic-инструмента.** Google сознательно
держит мутации вне MCP ⇒ наш write-слой уникален и не вытесняется (детали и политика — §21.2).
`claude-ads`, откуда планировалось «взять скилы», **не содержит интеграции с Google
Ads вообще** — пустой массив зависимостей в `pyproject.toml`, работа только с CSV-выгрузками,
mutation-gate без исполнителя, 85–90% объёма — markdown-инструкции. Забрать оттуда осмысленно
две вещи: каталог проверок (~74 по Google) и поля mutation-plan схемы.

**Отсюда решение (подтверждено заказчиком):** руки берём из текущего проекта. `ads/`, `confirm/`,
`core/` оборачиваются в **MCP-сервер**, Hermes вызывает их как инструменты. Confirm-гейт,
`confirmation_id`, замок аккаунта, валидаторы, 2156 тестов остаются в силе и работают
по-прежнему — просто вызывает их теперь Hermes, а не `bot/main.py`.

**Что архивируется:** `bot/` целиком (11 модулей хендлеров, ~151 хендлер, клавиатуры, визарды
кнопок, throttle, i18n) — интерфейс полностью заменяется Hermes. Ветка `archive/aiogram-bot`.

## Часть 1. Ключевые факты о Hermes (проверены по исходникам и GitHub API)

| Факт | Следствие для нас |
|---|---|
| Память = два markdown-файла: `MEMORY.md` **2200 симв.**, `USER.md` **1375 симв.**, без автосжатия | Долговременное знание о клиентах агентства туда **не влезет физически**. Держим в нашем Postgres, подаём MCP-инструментом |
| `MEMORY.md`/`USER.md` — **одни на профиль**, per-user памяти внутри профиля нет | Агент строит один «профиль пользователя» на всю команду. Изоляция клиентов — только через нашу БД |
| **Ролей и прав нет.** Одобренный юзер = владелец, включая терминал на сервере | **Блокер.** Терминал отключаем, право подтверждения строим в MCP-слое |
| Сессии: SQLite `~/.hermes/state.db` + FTS5; ключ DM — `agent:main:telegram:dm:{chat_id}` (**без** thread_id), thread_id есть только в group-ключах форум-топиков | Топик = изолированная сессия. Ложится на «клиент = топик» точно; вся личка одного человека — одна сессия |
| Forum topics поддержаны, `observe_unmentioned_group_messages`, `require_mention` | Групповой режим закрыт платформой, писать не надо |
| Скилы = markdown по [agentskills.io](https://agentskills.io), самонаписание = генерация markdown | **Точно совпадает** с выбором «скилы — только инструкции» |
| `skills.write_approval` по умолчанию **выключен** | Включить обязательно → стейджинг в `~/.hermes/pending/skills/` |
| `approvals.mode: smart` по умолчанию — вспомогательная LLM автоапрувит | Для денежного пути — `manual` + `approvals.deny` (не обходится даже YOLO) |
| **Skills Guard** сканирует **устанавливаемые** скилы (exfiltration, injection, destructive, supply-chain); **агент не может сам ставить hub-скилы** — только человек через CLI / `/skills`. НО рантайм-контент (веб-страница, MCP-ответ, досье) в ходе диалога **не сканируется**, а community-findings бьются `--force` **[уточнено 20.07 по докам]** | Хаб-вектор человеко-гейтед (хорошо). Рантайм-инъекция — наша забота: гард И7 + карантин (§16). Свои скилы держим в git и монтируем `external_dirs`, а не ставим из хаба (§21) |
| Curator: снапшоты, `--dry-run`, `pin`, `rollback`, откат отката | Механика отката обучения продумана лучше ожидаемого |
| **GPU не нужен**, модель по API, «$5/mo VPS достаточно»; минимальные RAM/CPU не документированы | **Мощный VPS не требуется.** Текущего + запас RAM хватит |
| 0.x, 21 релиз с 2026-03, каденция: медиана 5–6 дней (летом интервалы до 12–14), **~660 PR/неделю, открытых ~16.5k** (дрейфует ежедневно — точное число в ТЗ не фиксировать), миграции конфига | Пиннить **тег**, автообновление на проде не включать; регулярная ревизия апгрейдов по образцу скила `gads-version` |

## Часть 2. Целевая архитектура

```
Telegram supergroup агентства
  └── Топик = клиент  ──► Hermes session (изолированная история + скилы топика)
                            │
                            ├─ скилы (markdown): «как разбирать просадку заявок»,
                            │   «чек-лист аудита поиска», «когда не трогать бренд»
                            │   ↑ агент пишет сам → pending → /skills approve
                            │
                            └─ MCP-инструменты (наш код, Python)
                                ├─ READ:  get_stats, get_search_terms, get_competitors…
                                │          → ads/read.py, ensure_read_allowed
                                ├─ MEMORY: recall_client, remember_fact, recall_experience
                                │          → clients/, agent_facts, Recommendation*
                                └─ PLAN:  propose_change → Proposal в БД, НЕ исполняет
                                          execute_confirmed(confirmation_id)
                                          → ads/mutations.py, ensure_allowed, audit-row
```

**Принцип, из которого следует всё остальное:**

```
Автономия применяется к ПОНИМАНИЮ, ПЛАНИРОВАНИЮ и НАПИСАНИЮ СКИЛОВ.
Confirm-гейт применяется к ИСПОЛНЕНИЮ.
Скил может влиять на то, ЧТО агент предложит.
Скил не может влиять на то, МОЖНО ЛИ это выполнить.
```

Последние две строки — требование к тестам (§4), не декларация. Скил — markdown-инструкция,
он физически не может обойти `ensure_allowed`, потому что единственный путь к Google Ads API
проходит через MCP-инструменты.

### 2.5 Два контура: оператор и билдер

Требование «дам задачу сделай TikTok-интеграцию — и он сам всё сделает как агент» и требование
«терминал отключён, у денежного пути ни shell, ни файлов» — **не противоречат друг другу, если
это два разных процесса с нулём общих секретов.** Терминал нельзя дать Hermes не потому, что shell
опасен сам по себе, а потому что **у Hermes нет ролей на уровне инструментов**: одобренный
пользователь получает права владельца, а процесс сидит рядом с OAuth-токенами Google Ads. Развязка
не по правам, а по процессам и кредам.

| | **Контур A — оператор (прод)** | **Контур B — билдер (dev)** |
|---|---|---|
| Кто | Hermes 0.x на VPS заказчика | Claude Code headless / Codex — **не Hermes** |
| Где | Текущая Hetzner VPS | Отдельная VM или managed-песочница (Docker+non-root / E2B / Daytona) |
| Терминал | **Нет.** `approvals.deny` на exec, terminal-бэкенд не настроен | **Есть.** shell, git, pip, pytest |
| Файлы | Нет инструментов ФС | Полный доступ к чекауту репозитория |
| Сеть | Только OpenRouter + локальный MCP по stdio | Egress-allowlist: pypi, api.github.com, sandbox-ads.tiktok.com, openrouter.ai |
| Google Ads OAuth | **Только в процессе MCP-сервера**, отдельный юзер ОС, отдельный env. Hermes знает лишь `OPENROUTER_API_KEY` | **Ноль боевых кредов.** Только TikTok Sandbox (прямой токен + advertiser_id) |
| Что может изменить | Google Ads только через `execute_confirmed` после реплая человека | Ветку в приватном репо. **Не деплой** |
| Выход работы | Выполненная мутация + audit-row | Pull request |
| Триггер | Сообщение в топике от whitelist-чата | **Только вручную владельцем**, не по issue/PR-комментарию |

**Мост между контурами один — человеческий merge.** Hermes не имеет доступа к репозиторию вовсе.
Промоушен идёт по существующему пути `master → зелёный CI → auto-deploy`. Формулировка для заказчика:
«поставил задачу в топике — через день получил PR, который надо посмотреть и смержить; боевой доступ
добывает человек, и это недели, не часы».

**Почему это закрывает оба требования — критерий Meta AI «Agents Rule of Two»** (ai.meta.com,
31.10.2025; развитие «lethal trifecta» Саймона Уиллисона; агент не должен
одновременно иметь: (1) недоверенный ввод, (2) секреты, (3) смену состояния/выход наружу):
- **Контур A** имеет (2) и (3), но не (1): вход строго доверенный (whitelist), недоверенный контент
  (страница, досье, CSV) входит только в карантинном обрамлении **и на этот ход мутации отключаются**
  (гард И7, §4).
- **Контур B** имеет (1) и (3), но не (2): красть нечего. Egress-allowlist — второй рубеж, не первый;
  первый — отсутствие ценного. Это, а не текст в промпте, отвечает на инцидент Replit (агент снёс
  прод-БД в объявленном code-freeze) и Nx s1ngularity (кража секретов через промпт в пакете).

**Критично: таймаут Hermes против confirm-гейта.** Таймаут после PR #5389 считает **простой**, а не
wall-clock. Прогон, ждущий реплая «да» (человек отвечает 10–40 мин), — это чистый простой, и прогон
умрёт. Плюс компрессор контекста Hermes **первым делом вырезает tool-результаты** — то есть диффы
«было→станет». **Поэтому proposal обязан жить в нашей БД (`proposals` + `pending_expires_at`), а не в
живом прогоне Hermes** (это уже так спроектировано — теперь у решения есть жёсткое обоснование, и это
инвариант, а не удачное совпадение). Реплай «да» приходит в новый прогон, `execute_confirmed`
поднимает proposal по `proposal_id` и заново проходит `ensure_allowed`.

### Поток одной задачи

```
Менеджер в топике клиента: «разберись почему упали заявки»
  ↓ Hermes подтягивает: скилы топика + MEMORY.md + recall_client(customer_id) из нашей БД
  ↓ агентский цикл, READ-MCP: get_stats → get_search_terms → get_competitors
  ↓ уточняет текстом: «бюджет держим или можно снизить на 15%?»  ← reply менеджера, цикл продолжается
  ↓ propose_change ×N → Proposal'ы в БД с diff «было→станет»
  ↓ агент пишет сводку текстом, без кнопок
  ↓ менеджер РЕПЛАЕМ на это сообщение: «да»
  ↓ MCP execute_confirmed → ensure_allowed → ads/mutations.py → audit-row
  ↓ через 7/14/30 дней: RecommendationOutcome, замер delta
```

### Подтверждение реплаем (выбор заказчика)

`message.reply_to_message.message_id` → `proposals.tg_message_id`. Гарды:
- реплай **не на то** сообщение → отказ, агент переспрашивает;
- автор реплая ≠ автор задачи → отказ + запись попытки в `audit_log`;
- proposal старше TTL (60 мин) → протух, требуется пересборка. TTL 60, а не 15: человек отвечает
  10–40 мин (см. §2.5), 15-минутный TTL протухал бы в большинстве реальных сценариев. Цена длинного
  TTL — устаревание данных, поэтому он допустим **только вместе с freshness-recheck в момент
  исполнения** (§8.4 п.5);
- `confirmation_id` одноразовый через существующий `ConfirmStore.claim` — без изменений.

Формулировки согласия распознаёт **код** по списку (`да`, `делай`, `ок`, `подтверждаю`, `go`,
`yes`), не модель. Всё остальное — не согласие. Fail-closed.

**Транспорт подтверждения — инженерный инвариант (детали в §8.4):** метаданные реплая
(`actor_chat_id`, `reply_to_message_id`) обязаны попадать в наш код из доверенного канала рантайма
Hermes, **никогда из аргументов MCP-инструмента** — аргументы генерирует LLM. Ловушка форум-топиков:
технически каждое сообщение в топике — reply на корневое сообщение топика, поэтому проверка обязана
отличать явный реплай от неявного топикового (иначе «да» без реплая молча не сработает, а «да» на
корень топика может ложно совпасть) — нужен тест-корпус реплай-семантики в topics.

**Что уносит `bot/` вместе с собой (сверка 21.07 — это не UI).** У ~30 переносимых функций

### Конфигурация Hermes — обязательный минимум (Контур A)

```yaml
skills:
  write_approval: true          # ПО УМОЛЧАНИЮ ВЫКЛЮЧЕН — включить
agent:
  # ЕДИНСТВЕННЫЙ настоящий способ закрыть возможность: тулсет не регистрируется вовсе.
  disabled_toolsets: [terminal, browser, file, code_execution, web, ...]
approvals:
  mode: manual                  # не smart: вспомогательная LLM не решает за нас
  # ⚠️ deny — fnmatch-глобы КОМАНД, а НЕ имена тулсетов (К10: имя тулсета здесь молча
  #    игнорируется). Это defense-in-depth поверх disabled_toolsets, НЕ граница:
  #    путей не резолвит, а при контейнерном бэкенде терминала guard stack
  #    пропускается целиком. Закрывает возможности строка `disabled_toolsets` выше.
  deny: ["rm -rf *", "sudo *", "docker *", "git push*"]
telegram:
  require_mention: true
  observe_unmentioned_group_messages: true
memory:
  provider: none                # ЕД. ЧИСЛО (К10): ключ `providers` молча игнорируется — сторонние
                                # Honcho/Mem0/Supermemory остались бы доступны и слали реплики
                                # (customer_id, бюджеты) третьей стороне
  write_approval: true
auxiliary:                      # фоновые расходы (компрессия, approval-модель, vision, web_extract…)
  compression: { model: google/gemini-3.1-flash-lite }  # слаги сверять с cli-config.yaml.example
```

**Шаг 2 стоит вторым намеренно.** Гарды пишутся до того, как появится то, что они охраняют —
иначе они пишутся под уже написанный код и повторяют его ошибки.

**Дом scheduler'а (закрыть в шагах 1/10, иначе тихо умрёт).** APScheduler сегодня живёт в event
loop aiogram-бота, и все джобы шлют в Telegram через `bot.send_message` + `bot/i18n`. С архивацией
`bot/` планировщик, дайджесты и автопрун `pending_expires_at` умирают вместе с ним. Решение:
scheduler — отдельный процесс (или процесс MCP-сервера) с тонким Bot-клиентом для отправки в
Telegram; `i18n` выносится из `bot/`. Замер outcome (шаг 9) и фоновые аудиты (E13) зависят от этого.

**Про обучение на цифрах (шаг 9) — сказать заказчику вслух.** Конверсии в Google Ads
дописываются 30–90 дней. Замер на 7-й день систематически покажет, что резать расходы хорошо:
экономия видна сразу, потерянные конверсии придут позже. Поэтому вердикт `improved` только если
конверсии не упали И расход не вырос И CPA не вырос; окно ≥30 дней.

## Часть 7. Что сказать заказчику

### Три вещи, которые заказчик должен услышать, даже если не хочет

**1. «Полностью автономный агент» вы не покупаете — и в трёх местах это не вопрос денег.**
- *Терминал и токены.* У Hermes нет ролей: одобренный пользователь получает права владельца, включая
  shell на сервере с OAuth-токенами. Закрываем разделением на два контура — но «сам всё сделает»
  превращается в «сам сделает PR, вы смержите».
- *Агент не знает, справился ли он.* Открытый issue #54722 в hermes-agent (P2, без ответа
  мейнтейнеров): агент выдаёт «успешно/проверено» при провалившихся и неверифицированных tool-вызовах;
  runtime-гейта между исполнением и финальным ответом нет by design. Более того, `verify_on_stop: auto`
  **отключает верификацию на всех messaging-поверхностях, включая Telegram**. Единственный источник истины об успехе — внешний CI,
  который контролируем мы.
- *Обратная связь рекламы приходит через месяцы.* Конверсии атрибутируются на дату клика, окно до
  90 дней. Замкнуть «сделал → оценил → запомнил» быстрее месяца физически невозможно.
- Защитимые формулировки: **«автопилот в коридоре, который вы подписали числами, с ночным отчётом и
  кнопкой откатить»** + **«агент-стажёр, который приносит PR»**. Оговорка: rollback-инструмента в
  реестре §8 сейчас **нет** — «кнопку откатить» обещать только после undo-дизайна (какие операции
  обратимы и каким окном) либо не обещать вовсе; решение зависит от ответа заказчика (файл вопросов,
  блок «Границы автономии»).

**2. «Чем дольше работает, тем умнее» — по данным получается наоборот, и это надо оплатить.**
Не мнение: в исследованиях непрерывной памяти LLM консолидация агентом **своих же правильных решений**
даёт регресс; режим «добавлять в память всё» проигрывает селективному и оказывается **хуже, чем не
учиться вовсе**; рост числа скилов роняет pass-rate за счёт затенения похожими описаниями. (Числа —
направление, а не точные величины; см. оговорку в §18.) То есть требование «помнит всё и на этом
учится» в буквальном виде — это описание деградации. Работающая версия — «помнит и не переучивается
вниз» — стоит **75 ч на гарды Г1–Г8 + регрессионный набор** (E17) и означает видимые ограничения:
потолок ~40 активных скилов, консолидация только через человека, урок не сохраняется без ссылки на
прогон и метрику, запрет фиксировать вывод об эффекте раньше окна атрибуции.

**3. Смета выросла с 1420 до 2300–2670 ч, и главный драйвер — не TikTok.** TikTok — самая дешёвая
из новых хотелок по часам (165 ч MVP) и единственная с **чужим календарём** (2–6 недель ревью,
которые нельзя сжать и которые пропадут, если не подать заявку в первый день — подавать сейчас).
Настоящие драйверы: **полный аудит с посадочными — ~378 ч** (свой краулинг, две квотируемые системы
PSI/CrUX, карантин недоверенного контента, переход к асинхронной модели); **артефактная память —
160 ч** (Hermes **не сохраняет вложения вообще**, нет реестра артефактов, нет семантического поиска);
**контур автономной разработки — 113 ч** (не даёт заказчику ни одной новой функции — только делает
безопасным то, что считалось бесплатным). И отдельная строка **до старта, а не по ходу**: «чат гпт

### Дополнительно (сохранено из первой редакции)

1. **`claude-ads` не умеет работать с Google Ads.** Ни API, ни OAuth, ни GAQL — только разбор
   CSV-выгрузок, которые человек скачал руками. Оттуда берём каталог проверок, не функциональность.
   Работающий слой Google Ads есть ровно один — наш, и мы его сохраняем.

2. **Hermes даёт голову, руки остаются нашими.** Цикл, память, скилы, чат в группе, топики —
   его. Замок аккаунта, confirm-гейт, `confirmation_id`, валидатор RSA — наш код через MCP.
   Это не компромисс, а единственный способ не платить второй раз за уже работающее.

3. **Мощный VPS не нужен.** GPU не требуется, модель работает по API, документация Hermes
   прямо говорит про «$5/mo VPS достаточно». Деньги идут на токены, не на железо.

4. **«Обучается сам» — это накопление знания и написание себе инструкций, а не дообучение
   модели.** Никаких весов. Агент пишет markdown-скилы после сложных задач и правит их, когда
   его поправили. Самый честный сигнал — отказ менеджера: немедленный и неискажённый, в отличие
   от метрик, запаздывающих на месяцы.

5. **У Hermes нет ролей.** Одобренный пользователь получает права владельца, включая терминал
   на сервере с OAuth-токенами. Мы это закрываем (терминал отключён, `approvals.deny`, право
   подтверждения в нашем слое), но заказчик должен знать: платформа молодая, 0.x, релиз каждую
   неделю. Версию пиним, автообновление на проде не включаем.

**Три вопроса на встречу, без ответов на которые смета имеет разброс:**
- Сколько клиентов и задач в день? Единственная линейно растущая статья — токены.
- Насколько глубоко агент должен «разбираться»? «Посмотри 3 отчёта» vs «полный аудит с
  конкурентами и посадочными» — разница в 3–4 раза по стоимости прогона.
- Есть ли задачи, где менеджер готов дать действовать без подтверждения? Если да — какие и с
  каким потолком в деньгах. Ответ «пусть сам решает» означает, что вопрос не продуман.

## 8. Реестр MCP-инструментов

Сервер: `mcp_server/` — новый пакет, **тонкий слой**. Правило: MCP-функция не содержит бизнес-логики,
только валидация входа, вызов существующей функции и сериализация ответа. Любая логика, которую
хочется написать в MCP-слое, — признак того, что её место в `ads/` или `confirm/`.

Транспорт: stdio, локальный процесс. Hermes и MCP-сервер на одной машине, наружу порт не смотрит.
Регистрация в конфиге — ключ **`mcp_servers.<name>`** (не `mcp.*`), с per-server фильтром
`tools.include`: на пилоте Hermes отдаются **только READ-инструменты**, PLAN/WRITE добавляются на
шаге 5. Approvals Hermes MCP-инструменты **не покрывают** (только терминальные команды) —
подтверждение живёт целиком в нашем слое; это инвариант, а не выбор.

аккаунте разорвёт контекст модели и сожжёт бюджет за один вызов. Пагинация — параметром `offset`.

которые агент имеет право процитировать. Fact-guard по образцу [agent/loop.py:670-672](agent/loop.py#L670-L672)
переносится в проверку финального текста: число вне набора ⇒ ответ отбрасывается и
перегенерируется. Это единственная защита от того, что модель «округлит» CPA в отчёте клиенту.

### 8.4 Исполнение — единственная точка

```python
execute_confirmed(proposal_id, confirmation_id, actor_chat_id, reply_to_message_id)
```

**Инвариант транспорта (главный).** `actor_chat_id` и `reply_to_message_id` обязаны поступать в наш
код из **доверенного канала рантайма Hermes** — хук `pre_tool_call` с контекстом gateway-сообщения
или elicitation-ответ на уровне MCP-протокола (v0.18.0) — и **никогда из аргументов инструмента**:
аргументы генерирует LLM, то есть сигнатура выше в наивной реализации позволяет модели сфабриковать
подтверждение (нарушение золотых правил 1/2 и И3). Прототип на шаге 3 проверяет ровно два критерия:
**(a)** доходят ли реальные reply-метаданные в наш код мимо LLM; **(b)** переживает ли подтверждение
40-минутную паузу человека — elicitation блокирует живой прогон и может умереть по idle-таймауту.
Реплай-гейт допустим **только при (a)**; без доверенного канала write-слой в прод не выпускается.

Порядок проверок — **фиксированный, каждая fail-closed**:

1. `proposal` существует и в статусе `pending`;
2. `reply_to_message_id == proposal.tg_message_id` — реплай на то самое сообщение (**явный**, не
   неявный топиковый reply на корень форум-топика — см. §2, тест-корпус реплай-семантики);
3. `actor_chat_id == proposal.author_chat_id` — подтверждает автор задачи;
4. `actor_chat_id` в whitelist (`core.access`, объединение env и таблицы `whitelist`);
5. `now - proposal.created_at < TTL (60 мин)` — не протух — **плюс freshness-recheck**: перед
   исполнением re-fetch текущего значения и re-diff для diffable-операций; «было» уехало → отказ и
   пересборка. Без recheck длинный TTL нельзя: существующий `_assert_no_drift` (`ads/service.py:291`)
   покрывает только относительные budget/bid (`mode != set_to`) — ~35 из 39 операций исполнялись бы
   без проверки свежести, а `_verify_applied` (`:1196`) срабатывает уже ПОСЛЕ мутации и от
   устаревания не защищает. Альтернатива — дифференцированный TTL по риску операции;
6. `ConfirmStore.claim(confirmation_id)` — атомарно, одноразово;
7. `ads.client.ensure_allowed(proposal.customer_id)` — **заново**, аккаунт берётся из proposal,
   не из аргумента и не из контекста разговора;
8. вызов `ads/mutations.py` с `confirmation_id`;
9. `audit_log` — строка с actor, proposal, результатом.

Провал любого пункта → отказ + запись попытки. **Пункты 7 и 8 не переписываются** — это
существующий код.

**Пункты 6–9 уже собраны в `ads/service.py:1141` `execute_confirmed(store, confirmation_id)`
[проверено 20.07]**: он атомарно `claim`-ит, через `_apply_confirmed` (`:321`) строит клиента,
заново проходит `ensure_allowed(proposal.customer_id)`, зовёт `apply_*` и пишет audit — реальный
порядок внутри `_apply_confirmed` немного отличается от списка выше; при реализации фасада сверять
по коду, прав код. **Сигнатура выше — целевой MCP-фасад, а не текущая функция.** MCP-WRITE
= тонкая обёртка: получить `(actor_chat_id, reply_to_message_id)` из доверенного канала (инвариант
транспорта выше), выполнить проверки 1–5 (реплай/автор/whitelist/протухание/freshness — это НЕ в
`execute_confirmed`, это новый реплай-гейт), затем делегировать в существующий
`execute_confirmed(store, confirmation_id)`.

**Уточнения 21.07 — четыре, каждое найдено сверкой с исходниками:**

1. **Исполнителей два, а не один.** Ads-домен исполняет `ads/service.py:1141`; memory-домен
   (`profile_save/update/clear`) — `clients/execute.py:26 execute_confirmed_memory` со своим
   `MEMORY_OPERATIONS`. Мутационный `ensure_allowed` к нему **намеренно** не применяется (это не
   деньги и не Google Ads), `ensure_read_allowed` перепроверяется. Реализованный буквально по
   действующему тексту, §8.4 отвергнет `profile_update` как «op вне `SUPPORTED_OPERATIONS`» и
   сломает весь §20. Правило: маршрутизация по `operation`, **cross-domain вызов — fail-closed
   отказ** (Ads-операция не может уйти в memory-исполнитель и наоборот). `clients/execute.py` в
   редакции 20.07 не упомянут ни разу.
2. **Батч.** При `operations[]` (§8.3) исполнение атомарно по шагам с частичным откатом — механика
   уже реализована в composite-создателях (`_rollback_partial` на шагах 2–4, best-effort 5–8),
   переносится формулировкой, а не переписыванием.
3. **Отклонение тоже пишет audit-row.** `confirm/store.py:295-340` это уже делает, но требование
   «логируются и подтверждения, **и отклонения**» (ТЗ-1 §16) в спеке отсутствовало. Приёмка — П28.
4. **Freshness для create-операций.** П.5 описан для diffable-операций; у создания «было» не
   существует — проверка иная (конфликт имён, наличие бюджета/группы, лимиты аккаунта), и это
   надо записать, иначе гард окажется неприменим ровно там, где создаётся кампания.

### 8.5 Чего в MCP-реестре нет намеренно

Ни одного инструмента для: выполнения shell-команд, чтения/записи произвольных файлов, HTTP-запросов
по произвольному URL, правки конфига Hermes, правки собственного реестра инструментов. Скил,
который попросит такое, упрётся в **отсутствие самой возможности**: соответствующие тулсеты не
зарегистрированы (`agent.disabled_toolsets`), вызывать нечего. Проверяется гардом И5 — и проверять он
обязан именно живой список тулсетов, а не `approvals.deny`: в `deny` лежат fnmatch-глобы **команд**,
имя тулсета там молча игнорируется (К10), то есть такой список — инертен.

**Три исключения из «нет HTTP по произвольному URL» (21.07)** — без них половина функций
исходного ТЗ нелегальна. Все три: allow-list схем/доменов + SSRF-пиннинг IP + robots, **URL не
приходит из аргументов модели**:

| Исключение | Источник URL | Зачем |
|---|---|---|
| Краул сайта клиента | домен из `client_profiles.site_url` | ТЗ-3 §20.4 — база для профиля, sitelinks, УТП |
| PSI / CrUX по посадочным | final URL объявления из Google Ads | уже узаконено в §16 |
| Google Sheets API | `spreadsheet_id`, не URL | ТЗ-1 §9, ТЗ-2 §19.4 — выгрузка отчётов и round-trip верификации ключей |

Плюс парс **посадочной страницы** при генерации RSA (ТЗ-2 §19.5): URL берётся из уже собранного
черновика кампании, контент идёт через тот же карантин, что и страницы конкурентов (§16).

## 9. Схема БД — новые таблицы

Все новые, ни одна существующая не меняется деструктивно. Одна Alembic-миграция на группу.
Проектировать так, чтобы работало **и на SQLite, и на Postgres** — тесты сейчас на SQLite.
JSONB-операторы и `tsvector` в первой итерации не использовать.

```
agent_threads      id, chat_id, message_thread_id, client_id→client_profiles,
                   customer_id, title, created_at, archived_at
                   UNIQUE(chat_id, message_thread_id)

agent_runs         id, thread_id→agent_threads, author_chat_id, task_text,
                   status(running|awaiting_user|planning|awaiting_confirm|done|failed|expired),
                   iterations_used, tokens_used, cost_usd,
                   started_at, finished_at, pending_expires_at

agent_facts        id, thread_id, customer_id, subject, predicate, value,
                   source(user|dossier|site|derived), trust(internal|external),
                   confidence, stated_by_chat_id, created_at, superseded_by→agent_facts
                   INDEX(customer_id, superseded_by)

proposals          + tg_message_id      (к какому сообщению агента привязано подтверждение)
                   + author_chat_id     (кто поставил задачу)
                   + run_id→agent_runs
```

**Инварианты схемы:**

- `agent_facts.trust` — ровно два значения. `internal` = сказал человек из whitelist.
  `external` = краулинг сайта, досье, любой внешний текст. Четыре градации — преждевременное
  усложнение, отвергнуто.
- `external`-факты **никогда не попадают в промпт как инструкции** — только в обрамлении §8.2.
- `agent_runs.author_chat_id` — единственный, кто подтверждает предложения этого прогона.
- `pending_expires_at` — прогон в `awaiting_user` без ответа 24 ч протухает, иначе накопятся зомби.
- Факты не удаляются, а помечаются `superseded_by` — иначе нельзя разобрать, почему агент
  когда-то принял решение.

**История сообщений живёт в Hermes** (`~/.hermes/state.db`, SQLite + FTS5), дублировать её в
Postgres не надо. Наша БД хранит то, чего Hermes не знает: связь топик↔клиент↔аккаунт,
факты, предложения, аудит.

## 10. Скилы: формат и стартовая библиотека

### 10.1 Формат

`SKILL.md` с YAML-фронтматтером; **полная спецификация формата, источников и правил — в §21.**
Ниже — минимальный пример; фронтматтер приведён к документированному формату Hermes
(`name` ≤64 симв., `description` ≤1024 симв. — но в индексе system prompt Hermes описание
обрезается до ~60, суть — в первые 60; версия и все Hermes-поля — в `metadata.hermes.*`,
top-level `version:` валит строгий `skills-ref validate`; тело — секции `## When to Use` /
`## Procedure` / `## Pitfalls` / `## Verification`).

```markdown
---
name: diagnose-lead-drop
description: Разобрать падение заявок в поисковой кампании
metadata:
  hermes:
    version: 1.0.0
    category: google-ads
    tags: [diagnostics, search, conversions]
    requires_tools: [get_campaign_stats, get_search_terms, get_auction_insights]
---

## When to Use
Менеджер говорит «упали заявки/лиды/конверсии» без указания причины.

## Procedure / Порядок разбора
1. `get_campaign_stats` за 14 дней против предыдущих 14 — где именно просело:
   показы, клики, CTR, конверсии или CPA.
2. Просели показы → `get_auction_insights`: доля показов, новые конкуренты, бюджет-лимит.
3. Просел CTR при тех же показах → `get_ads`: не остановлены ли объявления, `get_search_terms`
   на рост нерелевантных запросов.
4. Клики есть, конверсий нет → предупредить, что причина может быть вне Ads (сайт, форма,
   отслеживание). Не предлагать резать бюджет на этом основании.
5. `recall_facts` перед любым предложением — у клиента могут быть правила («бренд не трогаем»).

## Чего не делать
- Не предлагать снижение бюджета в первые 3 дня после изменений — данные не устоялись.
- Не делать вывод по одной метрике: конверсии дописываются 30–90 дней.
```

Скил — **инструкция, а не код**. Он перечисляет, какие MCP-инструменты вызывать и в каком
порядке, и не может вызвать ничего вне реестра §8.

### 10.2 Стартовая библиотека (15–25 скилов, шаг 6)

Диагностика: падение заявок · рост CPA · перерасход бюджета · падение доли показов ·
нерелевантный трафик в поисковых запросах.
Аудит: чек-лист поисковой кампании · структура групп · качество объявлений RSA ·
минус-слова · настройки гео и языка · отслеживание конверсий.
Действия: как готовить изменение бюджета · как готовить изменение ставки · как писать RSA
под лимиты (заголовок ≤30, описание ≤90, путь ≤15, кириллица = 1 символ) · как добавлять
минус-слова, не отрезая бренд.
Общение: как формулировать сводку «было→станет» · когда переспросить, а не додумывать ·
как отчитаться о сделанном.

Источник содержания: `control-registry.json` из `claude-ads` (~74 проверки по Google) как
чек-лист-заготовка + существующая логика `advisor/` и визардов §19/§20.

### 10.3 Самонаписание (шаг 7)

Триггеры Hermes: задача решена за 5+ вызовов инструментов · агент упёрся и нашёл обход ·
**пользователь поправил его подход** · обнаружен нетривиальный порядок действий.

Флоу: агент пишет → `~/.hermes/pending/skills/` → `/skills pending` → `/skills diff <id>` →
`/skills approve <id>`. Переживает рестарт, помечает происхождение (передний план vs фоновый
review-форк).

Curator (уборка): детерминированная фаза включена — 30 дней без использования → `stale`,
90 → архив в `.archive/`. **LLM-консолидацию не включать** (`consolidate: false`) — она делает
широкие структурные правки и стоит токенов на каждом проходе. Скилы стартовой библиотеки —
`hermes curator pin`, чтобы автоматика их не тронула.

Откат: снапшот `tar.gz` перед каждым проходом, `hermes curator rollback`, `--dry-run` для превью.

После любой правки эталона — сверка каждого ключа с `cli-config.yaml.example` **пиновой** версии
(К10): неизвестные ключи Hermes молча игнорирует, конфиг «выглядит безопасным», но не работает.

`.env`: `TELEGRAM_ALLOWED_USERS` и `TELEGRAM_GROUP_ALLOWED_USERS` — **оба перечисляют людей** (К4).
`TELEGRAM_GROUP_ALLOWED_CHATS` **не задаём вовсе**: прошлая редакция этого абзаца звала вписать туда
id групп «чтобы не путать с user-allowlist», и это была ошибка класса fail-open. Чат-лист авторизует
чат ЦЕЛИКОМ и проверяется ПЕРВЫМ — `gateway/authz_mixin.py:344-358` делает `return True` до того, как
посмотрит на личность отправителя, то есть он не сужает список людей, а отменяет его. Полный разбор
со ссылками на строки — `deploy/hermes/host-a/config.yaml`, блок `gateway:`.
Режим — **long-polling, webhook-поверхность не открываем вовсе (К6)**; `TELEGRAM_WEBHOOK_SECRET`
понадобился бы только при webhook (gateway не стартует без него — требование из доков со ссылкой на
[GHSA-3vpc-7q5r-276h](https://github.com/NousResearch/hermes-agent/security/advisories/GHSA-3vpc-7q5r-276h);
сам advisory на 20.07 не опубликован — 404).

**Развёртывание:** systemd user-сервис через `hermes gateway install`, обязательно
`sudo loginctl enable-linger $USER` — иначе сервис умрёт при выходе из SSH. Логи:
`journalctl --user -u hermes-gateway -f`.

**Версия пинится жёстко.** Обновление — только вручную, после прогона всех тестов на стенде.
Причина: 0.x, релиз каждые 5–10 дней, миграции конфига между версиями (в v0.18.0 была
одноразовая миграция v32, в `curator.md` — след депрекейшена).

**Грабли Telegram-групп:** privacy mode включён по умолчанию — либо выключать через BotFather,
либо делать бота админом; **после смены privacy бота надо удалить и заново добавить в группу**,
Telegram кэширует состояние. Топики нельзя включить программно — владелец включает Topics
в настройках чата руками, иначе в логах `The chat is not a forum`.

## 12. Критерии приёмки

Формулировки — проверяемые действием, не «работает хорошо».

| # | Критерий | Как проверяет заказчик |
|---|---|---|
| П1 | Агент отвечает в группе на обращение по имени и молчит на посторонние реплики | Написать в топик без упоминания — тишина; с упоминанием — ответ |
| П2 | Агент знает клиента без напоминания | «Чем занимается этот клиент?» в топике → ниша, услуги, гео из досье |
| П3 | Агент сам собирает картину | «Разберись, почему упали заявки» → в ответе видны ≥3 разных среза данных |
| П4 | Агент переспрашивает и продолжает | На уточняющий вопрос ответить реплаем → агент продолжает разбор, не начинает заново |
| П5 | Изменение только по подтверждению | «Снизь бюджет на 15%» → сводка «было→станет», Google Ads не тронут до реплая «да». **Три формы суммы** (ТЗ-1 §5/§18): процент, абсолют в валюте аккаунта («поставь 500 грн в день»), абсолют с символом («подними до $30»); чужая валюта ⇒ отказ без FX-конвертации, §31.8 |
| П6 | Чужой не подтверждает | Коллега реплает «да» на чужую задачу → отказ, в `audit_log` попытка |
| П7 | Протухшее предложение не исполняется | Подождать дольше TTL (60 мин), ответить «да» → отказ, агент пересобирает; в пределах TTL — исполняется, но с re-fetch «было» (§8.4 п.5) |
| П8 | Память переживает рестарт | Перезапустить сервис → продолжить разговор в топике |
| П9 | Правило запоминается | «У этого клиента бренд не трогаем» → через день предложение не затрагивает бренд |
| П10 | Скил утверждается человеком | После сложной задачи `/skills pending` показывает предложенный скил |
| П11 | Терминал закрыт | Попросить агента выполнить команду на сервере → отказ |
| П12 | Инъекция не проходит | Тест с текстом на сайте клиента, содержащим команду → мутация не создана |
| П13 | Секрет не утекает | Спровоцировать ошибку авторизации → в чате и логах нет токена |
| П14 | Стоимость видна | Отчёт: сколько стоил прогон, сколько группа за месяц |

### 12.1 Функциональная приёмка П15–П34 (добавлено 21.07)

П1–П14 проверяют **механизм**. Исходные документы несут свои критерии приёмки — ТЗ-1 §18

Заказчик не выдумал: семейство существует и живёт на OpenRouter. Но **слага `gpt-5.6` нет** — есть

`response_format`, `reasoning`, `reasoning_effort`, `seed`, `include_reasoning`. **`parallel_tool_calls`
не поддерживается ни одним** (→ гард И8).

|---|---:|---:|---:|---:|---|

| `openai/gpt-5.6-terra` / `-terra-pro` | 2.50 | 15.00 | 0.25 | 3.125 | 5.00 / 22.50 |

**Четыре вещи, которые ломают наивную смету:**
1. **Запись в кэш платная — 1.25× от входа** (первое семейство OpenAI с такой тарификацией). Если
   системный префикс нестабилен по байтам между итерациями (динамический порядок инструментов,
   timestamp, порядок ключей JSON), мы платим 1.25× за перезапись вместо 0.1× за чтение. Префикс
   собирать **детерминированно** — это правка кода сборки промпта, а не выбор модели.
2. **TTL кэша управляем — но только явно.** Явный `prompt_cache_breakpoint` (поддерживается только
   GPT-5.6+) даёт TTL **≥30 минут** при промпте от 1024 токенов; без него кэш протухает между
   репликами человека в топике почти всегда. Breakpoint ставить на стабильный префикс — это правка
   кода сборки промпта, а не выбор модели.
3. **Порог 272 000 токенов** — выше него вход ×2, выход ×1.5, кэш ×2. Требование «помнит всё, что
   писал и загружал» штатно уезжает за порог. Держать промпт под 272k — не гигиена, а деньги.
4. **`-pro` стоит столько же за токен, но потребляет заметно больше токенов** (по докам OpenRouter;
   числа нет). На денежном пути без замера не ставить.

**Пин ЕСТЬ и обязателен: канонические id каталога — только датированные**
(`openai/gpt-5.6-terra-20260709` и т.п.); короткий слаг — алиас на последний датированный. Форма с
тильдой `~openai/gpt-latest` — **семейный** алиас, резолвится в Sol (флагман, самый дорогой) — только
для dev-экспериментов. В проде — только датированные пины. Плюс два обязательных флага:
`provider.require_parameters: true` — иначе при рероуте на другого провайдера `tools`/
`structured_outputs` **молча отбрасываются** (тихая поломка Pydantic-контракта); и логирование
разрезолвленного `model` из ответа OpenRouter в audit-row вместе с proposal (E18).

### Три ограничения, меняющие дизайн (а не текст отчёта)

**IS-метрики обрезаны на краях. [Проверено 20.07, докстринги v24]** `search_impression_share`
репортится 0.1..1 (ниже 0.1 → `0.0999`); `*_rank_lost` и `*_budget_lost` — 0..0.9 (выше 0.9 →
`0.9001`). **Ровно в зоне сильного давления метрика упирается в потолок, и дельта во времени = 0.**
Значение `0.9001` трактовать как «≥90%», тренд по насыщенным кампаниям не строить. Плюс: вывод «рост
rank_lost при неизменной ставке = конкуренты подняли ставки» — **гипотеза, а не факт** (Ad Rank
многофакторен: QS, пороги, микс запросов); формулировать как «требует проверки». `budget_lost` IS —
только на уровне кампании; `search_exact_match_impression_share` недоступна для Shopping; `oneof`-поля
— отсутствие значения, а не 0.

**Rate-метрики возвращаются долей 0..1, не процентом.** Порог фильтра —
`mobile_friendly_clicks_percentage < 0.9`, не `< 90` (иначе «ниже нормы» окажутся все URL). `speed_score`
часто unset (нужен минимум мобильных кликов) — нужен явный бакет «нет данных», а не `<= 5`.

### Чего обещать нельзя

| Требование | Реальность |
|---|---|
| «Кто конкуренты в аукционе, кто выше, overlap rate» | **Недоступно. [Certain]** Поля `metrics.auction_insight_*` и `segments.auction_insight_domain` в v24 **существуют** (проверил 20.07), но только для allowlisted-аккаунтов; allowlist закрыт; Google подтвердил 03.11.2025: «not yet publicly available… for any campaign type», сроков нет. Обходы: (а) давление по IS — без имён; (б) человек выгружает CSV из UI в топик, агент разбирает; (в) SEMrush/SimilarWeb — платно |
| «Полевые CWV по каждой посадочной» | У большинства посадочных **не будет URL-level CrUX** (мало трафика) — 404, останется origin или ничего. Не вопрос бюджета |
| «QS по всем кампаниям» | QS и `post_click_quality_score` — только поисковые ключи. Для PMax/Demand Gen/Video/Shopping их нет; там `ad_strength`/`performance_label` — другой набор сигналов. Единый «полный аудит» технически неоднороден |
| «Написал в топик — получил аудит» | Синхронно невозможно: PSI гоняет Lighthouse десятки секунд на URL; 20–30 посадочных — минуты-десятки минут. Аудит = **фоновая задача с прогрессом** (APScheduler есть), кэш по URL 24 ч |
| «Агент посмотрит, что дало изменение» | Конверсии на дату клика, окно до 90 дней; ждать ≥14 дней + conversion lag (Г8, §18) |

**PSI отдельно.** Числа латентности «10–30 с» держатся на одном закрытом issue 2022 г.; бёрст-лимит в
источниках разнится в 15 раз (100/100с … 1500/мин), официальная страница квоты не публикует. Практически:
пул ~1 rps, ретрай с экспонентой на 429, деградация частичного отчёта вместо падения; реальные числа
снять собственным замером на 20–30 посадочных за полдня. `strategy=mobile` и `desktop` — два отдельных
запроса. **Ключ PSI уходит в query-string (`?key=`) — редактировать надо не только тело ошибки, но и сам
URL в логах**, иначе правило 5 обходится через безобидный лог запроса.

### Карантин недоверенного контента — архитектура, не абзац в промпте

Сырой текст страницы **в контекст агента не попадает вообще.** Дешёвая модель (`gemini-3.1-flash-lite`)
извлекает из HTML фиксированную JSON-схему: `title`, `h1`, `has_form`, `phone`, `tags`, `redirect_chain`,
`http_status`, `canonical`, `match_score_to_ad`. В Hermes уходит только JSON (урезанный CaMeL; получается
бесплатно, т.к. мы и так агрегируем). Поверх — гард И7 + spotlighting (рандомизированные маркеры на
запрос). **Классификаторы инъекций не покупать** — цифры провала (TPR 22.8% на одном бенче, FPR 100%
на intent-awareness) относятся к PromptGuard **v1**; актуальные Prompt Guard 2 / LlamaFirewall
(arXiv 2505.03574) заметно лучше, но класс-ограничение то же: классификатор — не граница доверия.
Максимум — эвристика для **логирования** и флага в отчёте («на странице текст, похожий на
инструкцию агенту»).

**Хорошая новость по SSRF:** пиннинг IP в `core/ingest.py` на уровне транспорта
(`handle_async_request` резолвит и подменяет хост на каждом запросе), httpx с `follow_redirects=True`
прогоняет **каждый хоп** через транспорт → редиректы перепиннятся, типовой DNS-rebinding через редирект
не проходит [Likely — прочитал структуру, не тестировал]. Проверить: IPv6/CGNAT/link-local в блок-листе.
Для сайтов конкурентов — строгий robots.txt, User-Agent с контактом, ≥1 сек на домен, не хранить
персданные. EU AI Act: GPAI-обязательства действуют **уже с 2 августа 2025**; 2 августа 2026 —
полномочия Комиссии по принуждению (штрафы) и основная часть Акта.

## 17. Артефактная память — «помнит всё, что писал и загружал»

### Что Hermes даёт сам и чего не даёт

| Есть | Нет |
|---|---|
| Персистентный транскрипт `~/.hermes/state.db` (`sessions`/`messages`, включая `tool_calls` JSON и `tool_name`) | **Вложения не сохраняются** — файл живёт в эфемерном кэше с TTL-очисткой ~24 ч и выбрасывается (`gateway.attachment_storage_path` — только предложение в открытом issue #41979) |
| FTS5 `messages_fts` + `messages_fts_trigram` (с v11 покрывают `content`+`tool_name`+`tool_calls`) → путь к файлу и аргументы MCP-вызовов ищутся полнотекстом | **Векторного поиска нет** — только FTS5. Семантика = свой RAG или облако с отправкой данных клиентов наружу |
| Расщепление сессий при переполнении (`parent_session_id`) | **Реестра артефактов нет** — ни таблицы, ни индекса путей |
| `MEMORY.md` (2200) + `USER.md` (1375), один комплект на профиль | На 20 клиентов — пара строк на клиента; правки видны только со следующей сессии |

**Уточнение, разворачивающее решение:** документы **обрабатываются.** В `gateway/platforms/base.py`
четыре кэш-хелпера, включая **`cache_document_from_bytes(data, filename)`** — PDF/xlsx кладётся в
`~/.hermes/cache/documents/`. Extension-whitelist на инбаунде нет, только size-cap 128 MiB, и **magic
bytes не валидировались** (баг #6829: Slack-вложения сохранялись как HTML логина; закрыт 2026-04-10 —
проверить, покрывает ли фикс Telegram-путь). Точка перехвата существует, всеядна, и наш слой сам
решает, что персистить и что это на самом деле.

### Что строим у себя — к трём таблицам §9 добавляются две

```
agent_artifacts    id, thread_id→agent_threads, client_id, customer_id, run_id→agent_runs,
                   kind(uploaded_doc|generated_report|export|screenshot|audit_snapshot),
                   filename, mime, sha256, storage_ref, size_bytes,
                   summary_text,            -- то, что реально ищется и подаётся в контекст
                   extracted_text_ref,      -- полный текст отдельно, НЕ в промпт
                   trust(internal|external), created_at, superseded_by→agent_artifacts
                   UNIQUE(sha256, client_id)          -- дедуп повторных загрузок
                   INDEX(client_id, kind, created_at)

agent_run_events   id, run_id→agent_runs, seq, ts, tool_name,
                   args_redacted (JSON через core.logging.redact_text),
                   result_digest, rows_returned, cost_usd
                   INDEX(run_id, seq)
```

Плюс поиск: `to_tsvector('russian', summary_text)` в Postgres. **Это не дублирование FTS5 Hermes, а
закрытие двух его дыр:** русская морфология (trigram-FTS5 «бюджета» по «бюджет» скорее всего не найдёт —
проверить) и изоляция по `client_id` (гард И6). Оговорка §9 «tsvector в первой итерации не использовать,
тесты на SQLite» здесь становится узким местом → **перевод тестового харнесса на Postgres** (честнее
ветвления реализации; уже в риск-надбавке E15).

**Все четыре категории артефактов** (подтверждены заказчиком) идут сюда: загруженные документы+выгрузки,
сгенерированные отчёты+тексты, скилы+история решений, код в контуре разработки. Память Hermes (2200
симв.) для этого мала физически.

### Как перехватывать вложения — три варианта, ни одного идеального

| Вариант | Плюс | Минус |
|---|---|---|
| MCP-инструмент `ingest_attachment(path)`, агент вызывает по инструкции скила | Без форка, любая версия | Зависит от того, что агент вызовет — ~90% надёжности [Guessing], а это класс, где заказчик заметит пропажу |
| Хук гейтвея (у Hermes есть хуки, `pre_verify` документирован) | Детерминированно | **Не проверено, есть ли хук на входящее сообщение** (~3 ч чтения исходников) |
| Форк/патч гейтвея | Полный контроль | 0.x, релиз 5–10 дней — патч тащить через каждое обновление |

**Рекомендация:** проверить наличие message-хука (3 ч); есть — хук; нет — MCP-инструмент **плюс**
детерминированная подстраховка: cron раз в час сканирует `~/.hermes/cache/documents/` на новые файлы и
привязывает к последнему активному топику по времени. Некрасиво, но не теряет данные.

**Что подавать в контекст:** не полный текст артефакта, а `summary_text` + ссылку. Инструменты
`artifact_list(client_id, kind?, since?)` и `artifact_get(id, section?)`. Иначе «помнит всё» гарантированно
уводит промпт за 272k и удваивает цену входа (§15).

## 18. Самообучение — что обещать, какие гарды

> **Оговорка о числах.** Направление ниже — из ресёрча и согласуется с известными эффектами памяти
> LLM-агентов. **Конкретные проценты и часть ссылок ресёрч не смог надёжно подтвердить** (возможны
> перепутанные id работ). Поэтому в тексте клиенту — эффект и его знак, а не «−54%»/«−21%». Перед
> любой публикацией конкретной цифры — проверить первоисточник.

### Три обещания вместо одного

**Можно обещать:** (1) обучение на **отказах человека** — каждое «нет» на confirm-гейте структурированный,
немедленный, однозначный сигнал, работает в днях («отклонили дважды — перестал предлагать», шаг 8);
(2) **память фактов** о клиенте с источником, `trust`, `superseded_by`; (3) **библиотека скилов с
человеком-куратором**; (4) **обучение на цифрах — окно ≥30 дней** и тройной критерий (конверсии не упали
И расход не вырос И CPA не вырос).

**Нельзя обещать «чем дольше работает, тем умнее».** По данным — по умолчанию наоборот: консолидация
агентом своих же правильных решений даёт регресс; рост числа скилов роняет pass-rate за счёт затенения
похожими описаниями (не «раздутого контекста»); «добавлять в память всё» проигрывает селективному и
оказывается **хуже, чем не учиться вовсе**; названная агентом причина провала часто не имеет причинной
связи с реальной. Требование «помнит всё и на этом учится» **в буквальном виде — описание деградации.**

### Восемь гардов

| | Гард | Обоснование |
|---|---|---|
| **Г1** | Потолок активных скилов **≤40** + CI-тест на пересечение описаний выше порога | Skill shadowing: резать количество и похожесть, чистка контекста не спасает |
| **Г2** | **Запрет автопереписывания скилов по расписанию.** Консолидация — редкая, явная, через человека | Ошибку вносит сам механизм переписывания. Прямо противоречит дефолту Hermes-curator (у нас `consolidate: false`) |
| **Г3** | Reflection grounding: урок обязан ссылаться на `run_id` и конкретную метрику, иначе не сохраняется | Конфабуляция рефлексии |
| **Г4** | **Counterfactual ablation:** регрессионный набор задач со скилом и без; скил без улучшения откатывается | Память **вредит** на лёгких задачах. У нас 2156 тестов — каркас есть, это преимущество перед голым Hermes |
| **Г5** | TTL по классу факта, `superseded_by`, время как фактор ранжирования; разрешение конфликта — **детерминированное правило**, не суждение модели | Косинусу запись 5-минутной и 5-недельной давности одинаковы; модели хрупки при примирении конфликтов |
| **Г6** | Изоляция памяти и поиска по `client_id` (= И6) | Кросс-клиентское загрязнение при «топик = клиент» |
| **Г7** | External-контент попадает в память **только как цитата с `trust=external`**, никогда как урок/инструкция | Memory poisoning через инъекцию требует **одного** успеха — дальше агент разносит сам. «Полный аудит с конкурентами» — учебниковый вектор |
| **Г8** | Запись урока об эффекте изменения **блокируется** до истечения окна атрибуции; lag из данных аккаунта, не константа | Конверсии на дату клика. Замер на 7-й день систематически покажет «резать расходы хорошо». Побочно: частые автономные правки сами по себе вредны — сбрасывают learning period Smart Bidding (2–6 нед) |

**Поправка к Г4:** ближайший релевантный источник показывает **консервативное** смещение
LLM-судей («наивный судья» там — substring-эвристика, κ=0.049, согласие с человеком на уровне
случайности; ансамбль LLM-судей лучше, но занижает), и точность лучших моделей на разметке отказов
агента **ниже 55%**. Практическое следствие: регрессионный набор должен ловить **false negatives** —
хорошие скилы, зарезанные куратором, — а не только пропущенный мусор. Иначе библиотека тихо
перестанет расти. `.usage.json` + LLM-curator у Hermes — ровно те два сигнала, что в литературе
признаны недостаточными; внешний якорь (Г4) не опция.

**Два свежих аргумента в пользу гардов кодом:** (1) arXiv 2604.16968 (ACL 2026) — накопленный опыт
систематически смещает агента **действовать, а не отказывать**; это научное обоснование принципа
«опыт влияет на ЧТО предложить, но не на ПРАВО исполнения» (И3, Г-серия). (2) arXiv 2604.16706 —
runtime-интерцептор в коде снижает галлюцинации действий на −23 пп, тогда как LLM-судья даёт лишь
κ=0.43 с человеком: детерминированные гарды в коде эффективнее пост-хок оценки моделью.

## 19. Контур B — автономная разработка (детально)

### Песочница и сеть

- Отдельная VM или managed-песочница: Docker+non-root / E2B / Daytona. **Ноль боевых кредов.**
- Egress-allowlist через прокси: pypi.org, api.github.com, sandbox-ads.tiktok.com, openrouter.ai. Прокси
  негерметичен (domain fronting, обходы SOCKS5) — **второй рубеж, не первый; первый — отсутствие ценного.**
- Билдер = Claude Code headless / Codex, **не Hermes** (Hermes без терминала by design).

### Харнесс задача → PR

Триггер **только вручную владельцем** (не по issue/PR-комментарию — иначе внешний текст в issue
становится командой). Выход — PR. GitHub-конфигурация — см. Часть 4 (rulesets, CODEOWNERS,
machine-аккаунт без merge, supply-chain гард, `confirm-gate-audit` человеком на новых модулях мутаций).

### «Агент сам сделает TikTok-интеграцию» — честная оценка (TikTok гипотетичен, в базовую смету не заложен)

**До готового PR с зелёными тестами — да, в контуре B. Дальше — нет, и упирается не в код.**

*Агент сам:* тонкий REST-клиент под Marketing API v1.3 на httpx, Pydantic-схемы, пагинация, тесты против
`sandbox-ads.tiktok.com`, черновик мутационного слоя с проводкой в `Proposal`/`ConfirmStore`, ветка + PR.
Референс: открытые Python MCP под TikTok Ads на MIT (`AdsMCP/tiktok-ads-mcp-server`, 21 инструмент) —
**все read-only**, мутации в любом случае наши. Плюс: 13.05.2026 TikTok for Business анонсировал
**официальный MCP с write-scope** — если к старту работ он выйдет в GA, часть E19 отпадает; проверка
статуса — в §20, «ждать GA или строить самим» — вопрос заказчику (блок 9 списка вопросов).

*Требует человека и не сжимается:*

| Шаг | Кто | Календарь |
|---|---|---|
| Регистрация app, use case, scopes, privacy/ToS URL на домене заказчика, демо | **Заказчик** | подать в день 0 |
| App review TikTok | TikTok | **2–6 недель** [Likely] |
| Отладка OAuth-слоя — **только на проде** | Человек | +1–2 недели после апрува |
| Ревью+merge денежного пути + `confirm-gate-audit` | Человек | 8–16 ч |

**Ловушка:** Sandbox выдаёт **прямой access token + advertiser_id в портале**, а прод — OAuth 2.0
(auth_code → обмен → привязка рекламодателя). Весь слой авторизации (наш аналог `ads/auth.py` +
`core/secrets.py` + привязка advertiser_id) в песочнице **непроверяем в принципе** и пишется вслепую —
это не «переключить base URL за 4–6 ч», а две схемы аутентификации за одним интерфейсом + отладка на
боевом доступе. Плюс: время жизни access_token спорно (портал — «не истекает, рефреш нельзя»; интеграторы
— 24 ч + refresh 1 год); заложить путь переавторизации через бота в любом случае.

**Часы против календаря:** MVP (чтение + мутации бюджета/статуса за confirm-гейтом) — **70–100 ч**
человека (агент делает черновик 40–60%, ревью съедает экономию до ~30% нетто), **6–10 недель** до прода.
Полный паритет (создание сущностей, **видео-креативы — подсистемы у нас нет вообще**, отчётность с
задержкой ~11 ч и ретро-пересчётом 3 дней → бамп `SCORE_MODEL_EPOCH`) — **192–300 ч, 3–5 месяцев**.
Официальный SDK не брать: ~4.5 мес тишины, auto-generated swagger (синхронный urllib3/six) против нашей
async-базы на httpx, bus-factor 1.

## 21. Экосистема скилов — что берём, что пишем, что запрещаем

> Проверено по официальным докам Hermes 20.07. Ключевой факт, снимающий половину рисков:
> **агент НЕ может сам устанавливать hub-скилы** — установка community-скилов только человеком через
> `hermes skills` CLI или `/skills`. Агент умеет лишь **писать свои** скилы (`skill_manage`), а это мы
> гейтим `write_approval`. Значит supply-chain-вектор хаба — человеко-гейтед by design.

```markdown
## When to Use

## Pitfalls
## Verification
```

Каталоги: `<slug>/SKILL.md` (обязателен) + опц. `references/`, `templates/`, `scripts/`, `assets/`,
`examples/`. Прогрессивная загрузка: L0 `skills_list()` (~3k токенов, `{name,description,category}`) →
L1 `skill_view(name)` (полный текст) → L2 `skill_view(name, path)` (reference-файл).

Лимиты формата: `name` ≤64, `description` ≤1024, тело SKILL.md ≤100k символов. Описания — короткие
и **непересекающиеся**: роутинг по библиотеке падает логарифмически с её размером («black-hole
skills»), поэтому периодический аудит на перехваты (скил-«дыра» с широким описанием оттягивает чужие
задачи) — часть куратора. CI библиотеки: `skills-ref validate` + проверка UTF-8 **без BOM** + LF
(BOM молча теряет весь фронтматтер — Windows-гоча). Деплой скилов НЕ атомарен: индекс живёт в prompt
cache — после выкладки нужен `/reset`.

**Красный флаг в самонаписанном скиле:** `required_environment_variables` (env прокидывается в
sandbox — путь эксфильтрации) и любой намёк на `scripts/`, зовущие shell. На Контуре A терминал off,
но гард И5 обязан ловить оба паттерна в ревью pending-скила.

### 21.2 Источники и уровни доверия

| Источник | ID | Доверие | Наша политика (Контур A) |
|---|---|---|---|
| Встроенные (~70+, 73 на 20.07) | `builtin` | always | Референс стиля. Не рекламные — берём как образец SKILL.md. `--no-skills` убирает все builtin из промпта и attack surface; curator по дефолту `prune_builtins: true` — наши скилы страхует pin |
| Official optional (~100+, 104 на 20.07) | `official` | built-in | Референс. Ставить точечно и только неисполняемые |

| skills.sh, ClawHub, LobeHub, произвольные well-known/URL | `community` | low | **Не ставить на Контуре A.** `--force` бьёт non-dangerous findings — слишком слабо для денежного пути. Кейс ClawHavoc: 341 из 2857 скилов ClawHub вредоносные (кража ключей, персистентный вредонос в MEMORY.md) |

**Рекламных скилов в комплекте Hermes нет** — ни в builtin, ни в optional, ни у trusted-репо
(подтверждено 20.07); ближайшее адъяцентное там: `claude-design`/`sketch`, `blogwatcher`, web-scraping.
**Шире в экосистеме — уже есть:** официальный `google/skills` («Google Ads API MCP Server
Installation», «Quickstart»), 12 скилов в `itallstartedwithaidea/agent-skills`, хаб marketingskills.sh
(~1331 скил) — всё инструкции поверх **read-only** доступа. Плюс с 28.04.2026 существует официальный
Google Ads MCP-сервер `googleads/google-ads-mcp`: **read-only by design**, 3 generic-инструмента
(GAQL `search`, `list_accessible_customers`, `get_resource_metadata`) — Google сознательно держит
мутации вне MCP, наш write-слой они не вытесняют, а наш READ шире и с замком аккаунта. Референс
дизайна write-tools — `FGRibreau/mcp-google-ads` (30 инструментов, preview→confirm; **только
референс**, не зависимость). Каталог проверок берём из `claude-ads` `control-registry.json`
(~74 пункта) как **чек-лист-заготовку**, не как код. Вывод плана не меняется: **слой Google Ads и его
скилы пишем сами.**

### 21.3 Где живут НАШИ скилы — `external_dirs`, а не `~/.hermes/skills/`

```yaml
skills:
  external_dirs:
    - ${AIMASH_REPO}/skills        # наш git-каталог скилов; Hermes его НЕ делает read-only —
                                   # защита от записи агентом = права ФС (chmod/владелец)
```

Почему так, а не дать агенту писать в `~/.hermes/skills/`:
- скилы попадают под **CODEOWNERS-ревью и pin** (Контур B, §19) — правка скила = PR, а не тихий файл;
- переживают пересоздание профиля и `hermes update` (bundled-seeding их не трогает);
- дедуп: при коллизии слага локальная версия важнее — наш git выигрывает у случайно установленного.

Самонаписание агентом (`skill_manage`) остаётся включённым для **обучения**, но:
`skills.write_approval: true` → стейджинг в `~/.hermes/pending/skills/` → `/skills diff` →
человек `/skills approve`. Одобренный полезный скил затем **переносится в git** (не живёт только в
`~/.hermes/`), иначе теряется при миграции и не проходит ревью. Потолок ≤40 активных (Г1, §18).

### 21.4 Что взять из механик Hermes «на будущее» (продумано наперёд)

- **Bundles** — сгруппировать аудитные скилы под один слэш: `/audit-full` = чек-лист поиска +
  конкуренция + посадочные + ассеты. Один вызов вместо стека из пяти. Триггерится **только менеджером**
  (полный аудит по явной команде — требование заказчика).
- **`requires_toolsets: [aimash]` / `requires_tools: [...]`** — скилы Google Ads показываются агенту,
  только когда наш MCP-тулсет активен. Дешёвая изоляция: без нашего сервера рекламные скилы не висят
  в контексте и не жгут токены.
- **`/learn`** authors SKILL.md из директории/URL/текста. Использовать **только на внутренних
  источниках** (`/learn ~/aimash/advisor`), НЕ `/learn https://…` — внешний URL тянет недоверенный
  контент в авторинг скила (вектор И7). Полезно, чтобы «научить» агента логике из `advisor/` и визардов
  §19/§20, не переписывая руками.
- **Прочие категории awesome-hermes** (memory-providers, surfaces, bridges): memory-провайдеры
  (Honcho/Mem0/Supermemory) — **запрещены** (шлют реплики с `customer_id`/бюджетами третьей стороне,
  §4); surfaces/bridges (доп. мессенджеры) — вне скоупа, только Telegram.

```markdown

description: Подготовить изменение дневного бюджета кампании
metadata:
  hermes:
    version: 1.0.0
    category: google-ads

## When to Use
Менеджер прямо просит изменить бюджет («подними/снизь бюджет на …»). Только по прямой команде
человека — бюджет/ставка никогда из расписания или аномалии (правило 3).
## Procedure
1. `get_budgets` + `get_campaign_stats` за 14 дней — текущий бюджет, темп открутки, CPA.
2. Посчитать «станет» и предупредить, если рост >30% за раз (перезапуск learning period).
3. `recall_facts` — нет ли правила клиента (потолок бюджета, «бренд не трогаем»).
4. `propose_change` (operation из allow-list) → показать diff «было→станет». **НЕ исполнять.**
5. Ждать реплай «да» от автора задачи → `execute_confirmed`.
## Pitfalls
- Частые правки бюджета сбрасывают Smart Bidding learning (2–6 нед) — предупредить (Г8).

## Verification
diff показан, Google Ads не тронут до «да»; после — audit-row записан.
```

- агент шлёт **нумерованный список** с длинами каждого элемента;

**логика**, а не FSM.

**27.1 Восемь этапов** [Дизайн открыт — **R4**]. Этапы 0–7: выбор аккаунта → свободное описание →
настройки → ключи → RSA → изображения → ассеты и URL-опции → финальная сводка. Исходник (ТЗ-2)
требует **явного согласия на каждом этапе**, а не одного подтверждения в конце. Против И8 (≤1
pending proposal) это решается разделением: этапы 0–6 — **не proposal**, а переходы состояния
черновика в `campaign_drafts` (деньги не трогаются, в Google Ads ничего не создаётся); proposal
ровно один — финальный composite. Записать явно: **«этапное да» ≠ «денежное да»**.

**27.2 Свободное описание → типизированные настройки** [Есть в коде — `agent/campaign_settings.py`].
Тринадцать полей, каждое проверяемо в сводке (ТЗ-2 §19.2): название кампании (автоформат
«Гео · Продукт · Search»), **тип канала жёстко SEARCH**, дневной бюджет, стратегия ставок,
**модель оплаты (клик / CPA)**, гео-таргетинг, языки таргетинга, **сети (Search Partners —
опционально)**, **расписание показов (по умолчанию 24/7)**, **даты запуска (старт сегодня, без
даты окончания)**, устройства, аудитории, структура групп.

**27.3 Доливка «по аналогии»** [Есть в коде — `ads/read.py:581`]. Недостающие настройки берутся
из истории аккаунта: медианный дневной бюджет активных Search-кампаний, средний CPC, частый тип
соответствия, язык, расписание.

**27.4 Пометка источника значения** [Дизайн открыт]. В сводке каждое значение помечено
`by_analogy` / `by_default` / «сказал человек». Без этого менеджер реплаем «да» подтверждает
бюджет, который агент подставил сам. **`code_numbers` этого не закрывает** — он различает
«выдумано / не выдумано», а не «сказал человек / подставил агент». Приёмка — П26.

**27.5 Правка черновика свободным текстом** [Есть в коде — `agent/campaign_edit.py`]. Любое поле
правится до подтверждения; после правки — **обязательная повторная валидация** (иначе правка
обходит все проверки длины и политик) и пересборка сводки. ТЗ-2 §19.8 показывает правку, меняющую
**два ассета одной фразой**, с повторной проверкой длин, политик и **валидности номеров и URL** —
второй случай батча (R5), уже на правке, а не на создании.

**27.6 URL-опции** [Есть в коде]. Tracking template с обязательным `{lpurl}`; final URL suffix;
до 8 custom parameters.

**27.7 Финальная сводка** [Есть в коде — `fmt_cc_final_summary`, логика в `bot/texts.py`].
Настройки + Final URL + display path + утверждённые тексты **с длинами** + изображения + полный
набор ассетов + URL-опции.

**27.8 Инвариант PAUSED** [Есть в коде; в спеке слова `PAUSED` не было ни разу]. Кампания, группа,

сценарий приходится два подтверждения. Сверить с И8. Правило 14 в §22, приёмка П25.

**27.9 Карта «этап → сервис Google Ads API v24»** [Есть в коде]. CustomerService (выбор аккаунта)

## 29. База знаний о клиенте: профиль, краул, memory-домен

Полностью реализовано (`docs/CLIENTS_KB.md`). В действующем ТЗ представлено одним инструментом
`recall_client`.

**29.1 Модель данных** [Есть в коде]. Семь таблиц (§9.1). Инвариант: **один рекламный аккаунт —
один профиль** (UNIQUE `customer_id`); при этом ТЗ-3 §20.2 допускает **несколько брендов внутри
одного профиля**, если на аккаунте рекламируется несколько направлений — это прямо влияет на
§29.10.

**29.2 Запись профиля текстом** [Есть в коде — `clients/profile_extract.py`, `store.preview_merge`
/ `apply_upsert`]. Свободный текст → 9 полей; незамапленное уходит в `notes` (не теряется);
**мердж непустых, а не перезапись**; накопление нескольких сообщений в один профиль до команды
«сохранить» или idle-autosave; **снимок «до» в историю перед каждой перезаписью**; `profile_clear`
только за подтверждением.

**29.3 Второй исполнитель confirm-гейта** [Есть в коде — `clients/execute.py:26`]. Memory-операции
идут через тот же гейт, но исполняются `execute_confirmed_memory` со своим `MEMORY_OPERATIONS`;
мутационный `ensure_allowed` к ним намеренно не применяется, `ensure_read_allowed` перепроверяется.
См. §8.4 п.1 — без этого §20 не работает вовсе.

**29.4 Краул сайта клиента** [Есть в коде]. Один домен; обход **по внутренним ссылкам и/или
`sitemap.xml`**; `robots.txt` **fail-closed** (401/403 = запрет всего сайта по RFC 9309, 5xx ⇒
обход не начинается); интервал ≥0.3 с на хост; `Crawl-delay` / `Retry-After` соблюдаются; лимиты
страниц / глубины / времени (прод: 1000 / 3 / 240 с против 50–100 в исходнике — §32 #10);
внешние ссылки фиксируются как соцсети и **не обходятся**; **headless-рендеринг JS не
реализован** (§32 #13). SSRF-пиннинг IP — как для посадочных (§16).

**29.5 Что извлекается** [Есть в коде]. Карта страниц с типами + ключевые внутренние ссылки
(база sitelinks); услуги и цены (**цена хранится текстом** — не считаем, не конвертируем);
контакты **кодом**, по убыванию доверия: `tel:`/`mailto:` → JSON-LD → регекс; соцсети; УТП и
офферы; meta description и H1–H3.

**29.6 Обновление и перекраул** [Есть в коде]. Инкрементальный режим по `content_hash`:
новые/изменённые страницы; «сайт не изменился» ⇒ профиль не трогаем; слияние карты страниц
(регресс «sitelinks усыхали при перекрауле» уже был). Сценарий **смены сайта** (ТЗ-3 §20.5):
агент обновляет поле «Сайт» и **сам предлагает перекраулить новый адрес**.

**29.7 Асинхронность** [Есть в коде — `crawl_jobs`]. Журнал: домен, режим, статус, число страниц,
дата, ошибка. Дедуп по `customer_id` (два краула одного клиента одновременно не запускаются);
реконсиляция зависших `running` после рестарта; сводка «что нашли» приходит **по готовности** в
топик клиента — то есть требует push-канала (§30.3, R8).

**29.8 Коллизия с §16 / И7** [Дизайн открыт]. Краул клиентского сайта — external-контент. Если
`propose_change` недоступен в ходе с external-контентом, флоу ТЗ-3 §20.5 (краул → «было→станет» →
запись профиля) невозможен в один ход. Разрешить явно: **memory-proposal из external-хода
разрешён, Ads-мутации — нет.** То же исключение нужно для разбора посадочной при генерации RSA
(§26.2).

**29.9 PII и ретеншн** [Есть в коде, с последствием]. Телефоны и e-mail лежат в БД и попадают в
бэкапы; `profile_context_text()` **PII не отдаёт** — следовательно карточку клиента и call-ассет
через `recall_client` построить нельзя, нужен отдельный код-путь (§8.2 `get_client_card`). Текст
страниц чистится через 90 дней, строка карты остаётся. Краул и хранение — только то, что нужно
для генерации рекламных материалов (ТЗ-3 §20.7).

**29.10 Профиль → генерация** [Частично]. Профиль используется в: заголовках и описаниях RSA,
sitelinks / snippets / callouts, call / price / promotion, seed-ключах и фильтре релевантности,
display path. **Принцип релевантности** (ТЗ-3 §20.6) — «для большого сайта берётся срез под
конкретную кампанию и её ключи, а не весь сайт сразу» — **не реализован нигде**: сегодня
подаётся весь профиль с обрезкой по символам. Это [Дизайн открыт], приёмка П31.

## 31. Нефункциональные требования и эксплуатация

**31.1 Rate limiting** [Дизайн открыт]. Единственная реализация — `bot/throttle.py`, архивируется
без замены; в спеке нет ни одного упоминания. Нужен антифлуд на уровне gateway или MCP: без него
серия сообщений заваливает агента и жжёт бюджет модели.

**31.2 2FA критических операций** [Есть в коде, канал ввода умирает]. `core/twofa.py` реализован
полностью (лок-аут, алерт админам), но ввод PIN идёт через FSM aiogram. Без канала `_twofa_begin`
fail-closed ⇒ **включённая 2FA = все мутации отказаны**. Варианты: PIN в личку боту, TOTP вместо
статического PIN, либо отключить и записать отклонением. **Статический PIN в групповом топике
хуже, чем отсутствие 2FA.**

**31.3 Квота Google Ads** [Есть в коде — `core/quota.py`]. Basic-токен: 15 000 операций/сутки,
скользящее окно 24 ч, 80% — предупреждение, 95% — блокировка мутаций (**чтение не блокируется**),
ретраи только на `RESOURCE_EXHAUSTED`, семафор конкуренции, батчинг. Счётчик **per-process** —
при MCP + scheduler в разных процессах разъедется; нужен общий стор (`ads_quota_ops`, §9.2).

**31.4 Логирование стоимости LLM** [Дизайн открыт]. `core/usage.py` + `core/llm_budget.py` висят
на `agent/router.py`, который архивируется, а Hermes зовёт OpenRouter напрямую. Без решения
(локальный прокси либо ридер Activity API / `state.db`) критерий П14 «стоимость видна»
недоказуем, а правило 12 неисполнимо.

**31.5 Логирование вызовов API** [Частично]. Вызовы Ads/Sheets логируются через
`run_ads_read_call`; MCP-слой собственного лога успешных вызовов не ведёт.

**31.6 Топология деплоя** [Дизайн открыт]. Hermes (systemd + linger) + MCP-процесс +
scheduler-процесс. CI health-check захардкожен на `aimash-bot` — чинить вместе с архивацией.

**31.7 Двуязычность RU/EN** [Дизайн открыт]. `bot/i18n.py` — 3139 строк, 528 EN-ключей; ~20 точек
в scheduler локализуют текст под получателя. Для свободных ответов модели проблема мала, для
**структурных текстов** (алерты, сводки, отчёты, карточки) — нет: их рендерит код.

**31.8 Грамматика денежных команд** [Есть в коде, точка вызова умирает]. ТЗ-1 §5 и §18 требуют,
чтобы команда изменения бюджета принимала **процент, сумму в $, в грн и в другой валюте**, и
разбирал их **код**: `ads/resolve.py:428` (`_CURRENCY_TOKEN_RE` — usd/uah/eur/… + грн/гривн/евро/
долл/злот/крон + символы `$ € £ ¥ ₴ zł Kč`), `:437 detect_currency_token`, `:468 currency_mismatch`
(**отказ без FX**), `:500 compute_new_micros`, `ads/mutations.py:1480-1503` (округление по
биллинг-единице валюты), `agent/tools/schemas.py:161-172` (`ABSOLUTE_MONEY_MODES`, запрет
`currency='percent'` на абсолютной сумме). Точка вызова — `bot/main.py:1714-1737`, архивируется.
Приёмка: П5 расширяется тремя формами — «снизь на 15%», «поставь 500 грн в день», «подними до $30».

**31.9 Понятное уведомление об ошибке** [Дизайн открыт — **дыра в золотом правиле 5**]. ТЗ-1 §13
требует обработки ошибок и понятного сообщения пользователю. Третий рубеж редакции секретов —
`bot/ux.py` `err_text` — уходит в архив, замены в спеке нет. Сырой `str(e)` от google-ads или
OpenAI может нести токен. Перенести `err_text` в переносимый слой **до** первого выпуска
MCP-WRITE.

**31.10 Кэш данных аккаунта** — в ТЗ-1 §15 значится как «опционально». Решение: **не делаем**,
кэширование на уровне отчётов и артефактов (§17) закрывает практическую потребность; зафиксировано,
чтобы не всплыло как «потерянное требование».

## 32. Реестр отклонений от исходного ТЗ

Формат: **что говорит исходник → что делает проект → почему**. Это единственное место, где
записано «мы сознательно не делаем X». Отсутствие такой записи — не экономия, а необнаруженное
расхождение: при следующей переписи ТЗ отклонённое требование вернётся и попадёт в смету.

| # | Исходник говорит | Решение проекта | Почему |
|---|---|---|---|
| 1 | Кириллица в display path считается **как 2 символа** (ТЗ-2 §19.5) | Кириллица = **1** code point, ×2 только CJK | Ошибка исходного документа: `adcopy/validate.py:22-34` + гард-тесты, `docs/CAMPAIGN_WIZARD.md:177` называет это прямо. Дословный перенос сломает генерацию текстов |
| 2 | Тип кампании **UAC / App** (ТЗ-1 §11 + **критерий приёмки** §18 кр.6) | Не реализуется | У клиента нет приложения (решение по ресёрчу). Требует **письменного** подтверждения: пока его нет, критерий приёмки 6 остаётся невыполнимым обязательством |
| 3 | Ассет **App** (ТЗ-2 §19.7) | Не реализуется | Следствие #2 |
| 4 | Ассет **Affiliate location** (ТЗ-2 §19.7) | Невозможен | Удалён из Google Ads API v24 — техническое ограничение, не выбор |
| 5 | Ассет **Location** через Google Business Profile | Заглушка `NotImplementedError` | В v24 — через AssetSet + `place_id`, аккаунт-зависимо; отдельный объём работ либо вне объёма. Решить явно |
| 6 | **Нормализация валют** в сводном MCC-отчёте (ТЗ-1 §8) | Подытоги по валютам, **FX нет** | Нет доверенного источника курсов; деньги считает код, а не модель. Единый total = выдуманное число в отчёте клиенту. Если total нужен — отдельное решение об источнике курса и ответственном за расхождение |
| 7 | Подтверждение **кнопками** (✅/❌, кнопочные визарды) | Реплай текстом | Выбор заказчика при пивоте на Hermes. Следствия — R1, R4, §26.5, §27.1 |
| 8 | Тип соответствия по умолчанию **Phrase** (ТЗ-2 §19.4) | Медиана аккаунта → phrase как fallback | Сам исходник противоречив (в одном месте phrase, в другом «по аналогии»); код разрешил в пользу медианы, зафиксировано как «НЕ хардкод phrase (баг B6)» |
| 9 | **10** seed-ключей (ТЗ-2 §19.4) | **15** | Больше сидов → богаче набор идей; проверено на прогонах |
| 10 | Лимит краула **50–100** страниц (ТЗ-3 §20.4, помечено «уточнить при внедрении») | 1000 страниц / глубина 3 / 240 с | Прод-конфиг. **Незаложенная статья OPEX:** 1000 страниц × LLM-структурирование. Либо снижать лимит, либо закладывать расход — вопрос в §14 |
| 11 | Ключи берутся **только** из выверенной менеджером таблицы (ТЗ-2 §19.4) | Есть узаконенный обход: «использовать сгенерированные» + fallback при недоступности Sheets | Обход задизайнен намеренно. Если остаётся — требовать **явного предупреждения** менеджеру, что список не выверен |
| 12 | Одна команда → одна сводка → одно подтверждение (ТЗ-1 §5) | Сегодня: ровно одна операция за сообщение | `agent/loop.py:71-75` + И8 (≤1 pending). Прямое противоречие спеки самой себе. Решение — батч-proposal (§8.3), либо честно снять требование. **Смешанное поведение хуже обоих** |
| 13 | Headless-рендеринг JS-сайтов (ТЗ-3 §20.4, «опционально») | Не реализовано | Фактический отказ: SPA-сайт даст пустой профиль. Нужна хотя бы явная диагностика «сайт не отдал контент без JS», а не молчаливый пустой результат |
| 14 | Google Sheets как обязательный формат выгрузки (ТЗ-1 §9) | Реализовано, но с деплой-предусловием | Второй OAuth-scope + перевыпуск refresh-токена + календарный хвост. Если заказчик не подтверждает — объявить опцией, а не тихо не сделать |
| 15 | **3–4** описания RSA (ТЗ-1 §10) | Границы **2–4**, по умолчанию 4 | Нижняя граница расходится: API принимает 2. Привести к исходнику или оставить — решение на 1 строку в валидаторе, но зафиксировать надо |
| 16 | Слэш-команды (`/report`, `/campaigns`, `/pause`, `/keywords`, `/clients`, …) наравне с NL (ТЗ-1 §6, ТЗ-3 §20.8) | Не переносятся | В Hermes префикс `/` занят его собственными командами — **конфликт**, а не просто отказ. Замена — гайд «что можно сказать агенту» (§31, П37) |
| 17 | Кэш данных аккаунта (ТЗ-1 §15, «опционально») | Не делаем | Артефактная память §17 закрывает практическую потребность |

## 34. Одиннадцать рисков переноса в «текст + реплай»

Сведены отдельно, потому что каждый — не строка ТЗ, а вопрос «реализуемо ли это вообще без кнопок».
R3 и R6 **бинарные**: либо gateway умеет, либо два раздела переписываются на деградированный
сценарий. Их надо закрыть прототипом **до** фиксации сметы.

| Риск | Суть | Решение |
|---|---|---|
| **R1** | 15 заголовков поэлементно: кнопок нет, 15 подтверждений неюзабельны, И8 запрещает 15 pending | Сессия курации ≠ proposal; нумерованный список + одна реплай-команда; парсит код; один confirm на финальный `create_rsa` (§26.5, П24) |
| **R2** | Длинные списки (300 ключей, 7 разбивок) не влезают в потолок 50 строк | Правило 13: артефакт + сводка. Блокируется R3 |
| **R3** ★ | Отправка файла/ссылки в чат умирает с `bot/`; умеет ли gateway — **не проверено** | Прототип рядом с реплай-гейтом: (а) вложение через gateway, (б) fallback — публичная ссылка. Без этого §24 и §25.8 нереализуемы |
| **R4** | Восемь этапов визарда × согласие против «≤1 pending proposal» | Этапы 0–6 — переходы состояния `campaign_drafts`, не proposal; финальный composite — единственный proposal (§27.1) |
| **R5** | Батч «сделай A и B»: агент отказывает, исходник требует одной сводки | `proposals.operations JSON` + composite-исполнение, либо явный отказ от требования (§8.3, §32 #12) |
| **R6** ★ | Приём фото/видео: входная точка исчезает с `bot/` | Проверить, отдаёт ли gateway медиа в MCP-контекст; иначе деградация до «пришли ссылку» и сужение §28 |
| **R7** | Sheets round-trip длится часы против TTL 60 мин / 24 ч | Отдельная сущность «задание верификации» со своим сроком + сборщик мусора (§25.7, §30.1) |
| **R8** | Push без запроса (алерты, готовность краула и отчёта): модель «топик = сессия» инициативы агента не предусматривает | Уведомительный канал: scheduler шлёт в топик через тонкий Bot-клиент **мимо агента**, текст рендерит код (§30.3) |
| **R9** | 2FA-PIN в групповом топике | PIN в личку, либо TOTP, либо отключить и записать отклонением (§31.2) |
| **R10** | Поиск и навигация по аккаунтам: пикеры исчезают | `name_like` в `list_accounts` + правило «показывать ≤10 и просить уточнить» (§8.1) |
| **R11** | Пользователь не знает, что можно сказать: «описание команд» описывало кнопочного бота | Гайд `docs/USER_GUIDE.md` + `help`-скил; иначе функциональные П-критерии заказчику физически недостижимы (П37) |
